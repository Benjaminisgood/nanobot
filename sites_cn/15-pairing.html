配对鉴权

工作区围栏挡住的是工具；配对挡住的是谁能跟 bot 说话。 默认不是「网上任何人私聊你都能驱动 exec」。实现只有一个小 JSON 文件加一把线程锁。

一、三道门：星号、白名单、配对库

    def is_allowed(self, sender_id: str) -> bool:
        """Check sender permission: star > allowlist > pairing store > deny."""
        if isinstance(self.config, dict):
            config_mapping = cast(dict[str, Any], self.config)
            allow_list: Any = (
                config_mapping.get("allow_from") or config_mapping.get("allowFrom") or []
            )
        else:
            allow_list = getattr(self.config, "allow_from", None) or []
        if "*" in allow_list:
            return True
        # allowFrom entries are opaque tokens — must match exactly.
        if str(sender_id) in allow_list:
            return True
        if is_approved(self.name, str(sender_id)):
            return True
        return False
条件结果
allowFrom 含 "*"全部放行（公开 bot，自行承担风险）
发送者字符串精确在名单里放行。注释强调是 opaque token，不要做模糊匹配
pairing.json 的 approved 集合主人批准过的 DM 发送者
以上都不是拒绝。私聊发配对码，群聊只打日志

_handle_message 用 authorization_id or sender_id 做检查。 群场景可以把「房间」当作授权主体，同时 inbound 上仍记录真实 sender——身份和权限解耦。

二、陌生人私聊：发码，不进总线

未授权且 is_dm 时，不会 publish_inbound：

        permission_id = authorization_id if authorization_id is not None else sender_id

? 为什么群聊不发配对码

群是共享空间：把一次性码贴进群等于公开邀请所有人去找主人批准。 未授权群消息只 warning，等你把群 id 写进 allowFrom。

三、pairing.json：小文件 + 线程锁

路径在数据目录下（默认 ~/.nanobot/pairing.json）。 用 threading.Lock 而不是 asyncio 锁：CLI 的 /pairing 和异步渠道 handler 都能调。 

def generate_code(
    channel: str,
    sender_id: str,
    ttl: int = _TTL_DEFAULT_S,
) -> str:
    """Create a new pairing code for *sender_id* on *channel*.

    Returns the code (e.g. ``"ABCD-EFGH"``).
    """
    with _LOCK:
        data = _load()
        _gc_pending(data)
        raw = "".join(secrets.choice(_ALPHABET) for _ in range(_CODE_LENGTH))
        code = f"{raw[:4]}-{raw[4:]}"

        data.setdefault("pending", {})[code] = {
            "channel": channel,
            "sender_id": str(sender_id),
            "created_at": time.time(),
            "expires_at": time.time() + ttl,
        }
        _save(data)

approve_code 从 pending pop 掉，写入 approved[channel] 集合。 is_approved 读失败（OSError）返回 False——fail closed， 磁盘坏了不会突然变成对全世界开放。

▲ 易错点：生成码失败 vs 检查失败

generate_code 抛 OSError 时渠道选择「不回配对码、也不崩 handler」—— 避免 I/O 故障变成对陌生人的拒绝服务放大器（反复崩溃重启）。 is_approved 同样 I/O 失败则当未批准。 两个方向都偏「宁可少理人，也不要误放行 / 不要把进程打挂」。

四、/pairing 是纯函数式入口

handle_pairing_command 除了改 store 没有别的副作用， CLI 和 CommandRouter 共用。子命令包括 list / approve / deny / revoke。

五、练习

基础Telegram 配置 allowFrom: ["*"] 时，还需要配对吗？

不需要。 "*" 第一道门直接 True，后面白名单和 pairing store 都不会走到。 这适合你明确想做公开 bot 的场合；私人助手请不要用星号。

进阶未授权用户在群里 @bot。会不会收到配对码？消息会不会进入 AgentLoop？

都不会（除非该群的 authorization_id 已在白名单）。 非 DM 分支只打 warning 然后 return，没有 inbound。 配对码只在 is_dm 为真时生成。

挑战攻击者枚举配对码。设计上有哪些减速/失效因素？还缺什么（源码里没有的）？

有的：secrets.choice 字母表随机、ABCD-EFGH 形态、pending TTL、 批准后从 pending 删除。approve 用精确字符串，没有「差一位也行」。

源码没有：按 IP / 发送者的尝试次数上限、验证码字母的混淆（I/O/0/1 是否排除要看 _ALPHABET）、 多因素。这是「私人助手规模」的文件库，不是 IdP。 真正的防线是码只出现在私聊、且必须由已授权的主人执行 approve。
