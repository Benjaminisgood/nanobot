第 07 章 · 能力层

记忆与上下文压缩

第 03 章的 build 阶段会在调 LLM 前压缩会话；第 04 章的 Runner 只消费 get_history() 返回的消息列表。这一章我们读记忆到底存在哪、怎么写盘、 怎么压缩、压缩后 LLM 还能看到什么——横跨 memory.py、 session/manager.py、autocompact.py 与 goal_state.py。

一、三层存储：活会话、归档、长期知识

nanobot 不把"记忆"塞进一个巨型文件。它按生命周期分成三层， 每层有不同的读写模式和崩溃语义：

层路径格式职责
会话 transcript {workspace}/sessions/{base64url(session_key)}.jsonl JSONL 当前会话的完整消息流 + metadata + 可选 provider_state
压缩归档 {workspace}/memory/history.jsonl append-only JSONL（带 cursor） Consolidator 把旧消息摘要后追加到这里
长期知识 SOUL.md / USER.md / memory/MEMORY.md Markdown Dream 阶段二编辑的 durable memory，Git 跟踪变更

默认 workspace 是 ~/.nanobot/workspace/（config/paths.py:51-54）。 会话文件名的编码逻辑在 JsonlSessionStore.storage_key()： 

    def storage_key(key: str) -> str:
        return base64.urlsafe_b64encode(key.encode()).decode().rstrip("=")
? 为什么不能直接用 session_key 当文件名

典型 session_key 形如 telegram:123456:topic:7，含冒号 :。 在 Windows 上冒号是非法文件名字符；在 POSIX 上虽然合法，但路径解析和 shell 转义都会踩坑。 base64url 编码把任意 UTF-8 字符串映射成文件名安全字符，且可逆—— decode_storage_key() 能从文件名还原原始 key。

同文件里还有一个 safe_key()（把 : 替换成 _）， 那是遗留路径的兼容方案；新写入一律走 base64url。

二、JSONL 会话文件结构

每个 .jsonl 文件的第一行固定是 metadata 记录， 可选第二行是 provider_state，之后才是消息行。写入逻辑在 JsonlSessionStore.save()： 

    def save(self, session: Session, *, fsync: bool = False) -> None:
        path = self.get_session_path(session.key)
        tmp_path = path.with_suffix(".jsonl.tmp")

        try:
            with open(tmp_path, "w", encoding="utf-8") as f:
                metadata_line = {
                    "_type": "metadata",
                    "key": session.key,
                    "created_at": session.created_at.isoformat(),
                    "updated_at": session.updated_at.isoformat(),
                    "metadata": session.metadata,
                    "last_consolidated": session.last_consolidated,
                }
                f.write(json.dumps(metadata_line, ensure_ascii=False) + "\n")
                if session.provider_state is not None:
                    provider_state_line = {
                        "_type": _PROVIDER_STATE_RECORD_TYPE,
                        "state": session.provider_state.to_private_record(),
                    }
                    f.write(json.dumps(provider_state_line, ensure_ascii=False) + "\n")
                for msg in session.messages:
                    f.write(json.dumps(msg, ensure_ascii=False) + "\n")
                if fsync:
                    f.flush()
                    os.fsync(f.fileno())

            os.replace(tmp_path, path)

            if fsync:
                with suppress(PermissionError):
                    fd = os.open(str(path.parent), os.O_RDONLY)
                    try:
                        os.fsync(fd)
                    except OSError as exc:
                        if exc.errno != errno.EINVAL:
                            raise
                    finally:
                        os.close(fd)
        except BaseException:
            tmp_path.unlink(missing_ok=True)
            raise

注意 last_consolidated 写在 metadata 行里——它是归档进度指针， 不是"删掉了多少条消息"的计数器。后面第七节会讲它如何影响 get_history()。

三、原子写入 + fsync：本章核心机制

会话和归档文件都走同一套模式：写临时文件 → flush + fsync → os.replace。 归档侧的完整实现在 MemoryStore._write_entries()： 

    def _write_entries(self, entries: list[dict[str, Any]]) -> None:
        """Overwrite history.jsonl with the given entries (atomic write)."""
        tmp_path = self.history_file.with_suffix(self.history_file.suffix + ".tmp")
        try:
            with open(tmp_path, "w", encoding="utf-8") as f:
                for entry in entries:
                    f.write(json.dumps(entry, ensure_ascii=False) + "\n")
                f.flush()
                os.fsync(f.fileno())
            os.replace(tmp_path, self.history_file)

            # fsync the directory so the rename is durable.
            # On Windows, opening a directory with O_RDONLY raises
            # PermissionError — skip the dir sync there (NTFS
            # journals metadata synchronously).
            with suppress(PermissionError):
                fd = os.open(str(self.history_file.parent), os.O_RDONLY)
                try:
                    os.fsync(fd)
                finally:
                    os.close(fd)
        except BaseException:
            tmp_path.unlink(missing_ok=True)
            raise

四个要点，缺一不可：

  1. 写 tmp → os.replace。 崩溃时读者要么看到旧版完整文件，要么看到新版完整文件—— 不会出现"写到一半"的损坏 JSONL。异常时 tmp_path.unlink(missing_ok=True) 清理垃圾。
  2. f.flush() + os.fsync(f.fileno())。 flush 只把 Python 缓冲推到 OS 页缓存；fsync 才保证数据真正落盘。 没有 fsync，进程被 kill 后可能丢最后几 KB。
  3. 目录 fsync。 POSIX 下 rename 本身不保证跨崩溃可见——目录项更新也需要 fsync。 这是 SQLite、LevelDB 等成熟存储的通用做法。
  4. Windows 例外。 目录 O_RDONLY 会 PermissionError，用 suppress 跳过； NTFS 对元数据日志同步写入，实践中可接受。
◆ 核心要点：性能与耐久性的权衡

会话侧 save(session, fsync=False) 是默认热路径—— 每个回合可能写盘多次，每次都 fsync 会显著拖慢响应。 关机时 SessionManager.flush_all() 才强制 fsync=True： 

    def flush_all(self) -> int:
        """Re-save every cached session with fsync for durable shutdown.

        Returns the number of sessions flushed.  Errors on individual
        sessions are logged but do not prevent other sessions from being
        flushed.
        """
        flushed = 0
        cached = dict(self._overflow_cache.items())
        cached.update(self._cache)
        for key, session in cached.items():
            try:
                self.save(session, fsync=True)
                flushed += 1
            except Exception:
                logger.warning("Failed to flush session {}", key, exc_info=True)
        return flushed

设计取舍：正常运行时容忍"最后一秒"的数据丢失风险，优雅关机时补齐耐久性。 第 03 章调试技巧里提到 save 阶段慢通常是 fsync—— 如果你在生产环境强制每次 fsync，latency 会明显上升。

四、Dream 两阶段记忆整合

AGENTS.md 称这套机制为 "Dream two-phase memory consolidation"。 文档详见 docs/memory.md:28-63。数据流如下：

阶段一 Consolidator（热路径，回合内/回合后触发） session.messages[0 .. last_consolidated) │ LLM 摘要（失败则 raw_archive 降级） ▼ memory/history.jsonl ← append-only，每条带 cursor │ 推进 session.last_consolidated 指针 ▼ session.messages 文件里消息仍在，但 get_history() 不再回放旧段 阶段二 Dream（冷路径，cron 默认每 2h / 手动 /dream） history.jsonl（cursor > .dream_cursor） │ build_dream_prompt() 嵌入 SOUL/USER/MEMORY 当前内容 │ 受限工具集：Read / Edit / Write / ApplyPatch ▼ 编辑 SOUL.md / USER.md / memory/MEMORY.md │ set_last_dream_cursor() 推进 │ Git 提交 + compact_history() 裁剪旧归档 ▼ 长期知识文件更新完毕

4.1 阶段一：Consolidator.archive()

    async def archive(
        self,
        messages: list[dict[str, Any]],
        *,
        runtime: LLMRuntime,
        session_key: str | None = None,

        ``summary_messages`` adds context but is excluded from raw fallback.
        """

                model=runtime.model,

                    {

                tool_choice=None,
                temperature=runtime.generation.temperature,
                max_tokens=runtime.generation.max_tokens,
                reasoning_effort=runtime.generation.reasoning_effort,

4.2 阶段二：Dream prompt 与完成判定

    def build_dream_prompt(self, *, max_entries: int = 20) -> tuple[str, int] | None:
        """Build the Dream prompt with unprocessed history context.

        Returns ``(prompt, last_cursor)`` or ``None`` if nothing to process.

        The current contents of the durable memory files (SOUL.md, USER.md,
        memory/MEMORY.md) are embedded so the model edits the real files rather
        than a stale mental model — eliminating a class of failed/out-of-bounds
        edits that previously produced hallucinated audit records.
        """
        last_cursor = self.get_last_dream_cursor()
        entries = self.read_unprocessed_history(since_cursor=last_cursor)
        if not entries:
            return None

        batch = entries[:max_entries]
        history_text = "\n".join(
            f"[{e['timestamp']}] {truncate_text(e['content'], 1000)}"
            for e in batch
        )
        template = self._dream_template()
        files_section = self._render_current_memory_files()
        prompt = (
            f"{template}\n\n{files_section}\n\n"
            f"## Conversation History\n{history_text}"
        )
        return (prompt, batch[-1]["cursor"])

docstring 里那句 "edits the real files rather than a stale mental model" 是关键设计决策—— Dream 必须把当前文件内容嵌进 prompt，否则模型会基于过时的 mental model 做无效编辑。

六、压缩边界只在 user turn 处切

    def pick_consolidation_boundary(
        self,
        session: Session,
        tokens_to_remove: int,
    ) -> tuple[int, int] | None:
        """Pick a user-turn boundary that removes enough old prompt tokens."""
        start = session.last_consolidated
        if start >= len(session.messages) or tokens_to_remove <= 0:
            return None

        removed_tokens = 0
        last_boundary: tuple[int, int] | None = None
        for idx in range(start, len(session.messages)):
            message = session.messages[idx]
            if idx > start and message.get("role") == "user":
                last_boundary = (idx, removed_tokens)
                if removed_tokens >= tokens_to_remove:
                    return last_boundary
            removed_tokens += estimate_message_tokens(message)

        return last_boundary
▲ 易错点：为什么不能从任意消息处切断

OpenAI/Anthropic 的消息序列有合法性约束：每个 assistant 消息的 tool_calls 必须紧跟着对应数量的 role="tool" 结果。 如果在 tool-call 序列中间切断并归档前半段，剩余消息的序列就非法—— API 直接 400 拒绝。

所以边界只能选在 role == "user" 处——那是自然的新回合起点。 第 03 章注入队列的"安全注入点"也是同一类约束的不同侧面。

七、压缩后「给 LLM 看什么」

关键洞察：压缩不是删掉 JSONL 里的消息，而是移动 last_consolidated 指针 + 保留最小可回放后缀。 核心逻辑在 Session.get_history()： 

    def get_history(
        self,
        max_messages: int = FILE_MAX_MESSAGES,
        *,
        max_tokens: int = 0,
        extend_to_user: bool = False,
        include_runtime_context: bool = True,
    ) -> list[dict[str, Any]]:
        """Return recent replayable messages for LLM input.

        History is sliced by message count first (``max_messages``), then by
        token budget from the tail (``max_tokens``) when provided.
        """
        replay_start = self.last_consolidated
        if replay_start:
            # ``last_consolidated`` is archive progress, not a replay boundary.
            # Keep a small raw suffix for continuity, extending back to the user
            # that started an assistant/tool sequence when necessary.
            recent_start = recent_message_start_index(
                self.messages,
                MIN_COMPACTED_REPLAY_MESSAGES,
                extend_to_user=True,
            )
            replay_start = min(replay_start, recent_start)

        replayable = self.messages[replay_start:]
        max_messages = max_messages if max_messages > 0 else FILE_MAX_MESSAGES
        unarchived_count = len(self.messages) - self.last_consolidated
        if replay_start < self.last_consolidated and unarchived_count < max_messages:
            # The archived replay suffix can exceed the nominal count when one
            # tool-heavy turn spans the boundary. Preserve that complete turn.
            start_idx = 0
        else:
            start_idx = recent_message_start_index(
                replayable,
                max_messages,
                extend_to_user=extend_to_user,
            )
        sliced = replayable[start_idx:]

读这段代码的三个要点：

  1. last_consolidated 是归档进度指针，不是 replay 边界。 即使已归档，也至少保留 MIN_COMPACTED_REPLAY_MESSAGES = 8 条尾部消息（manager.py:39）。
  2. recent_message_start_index(..., extend_to_user=True) 会回溯到起始 user 消息，避免从 assistant/tool 序列中间开始回放。
  3. 后续还有 find_legal_message_start(sliced)（manager.py:247-250） 清理开头的孤立 tool result。
◆ 核心要点

文件里 2000 条消息，LLM 可能只看到最后 120 条—— 但中间被"跳过"的消息已经摘要进了 history.jsonl， Dream 阶段二会进一步提炼进 Markdown 长期知识。 三层存储 + 指针语义让"压缩"对上层透明。

八、TTL 自动压缩的真实位置

▲ 易错点：不在 session/manager.py

空闲压缩实现在 nanobot/agent/autocompact.py， 由 AgentLoop._check_expired_sessions_if_due()（loop.py:1142-1152） 在调度循环的 1 秒超时心跳里周期调用——和第 03 章讲的"心跳设计"是同一套机制。 

    def _check_expired_sessions_if_due(self) -> None:
        """Scan idle sessions no more often than the configured interval."""
        now = time.monotonic()
        if now < self._next_idle_compact_check_at:
            return
        self._next_idle_compact_check_at = now + self._idle_compact_check_interval_s
        self.auto_compact.check_expired(
            self.schedule_background,
            self.runtime_for_session,
            active_session_keys=self._pending_queues.keys(),
        )
    def _is_expired(self, ts: datetime | str | None,
                    now: datetime | None = None) -> bool:
        if self._ttl <= 0 or not ts:
            return False
        try:
            if isinstance(ts, str):
                ts = datetime.fromisoformat(ts)
            current = now or datetime.now()
            if getattr(ts, "tzinfo", None) is not None or current.tzinfo is not None:
                idle_seconds = current.timestamp() - ts.timestamp()
            else:
                idle_seconds = (current - ts).total_seconds()
        except (OSError, OverflowError, TypeError, ValueError):
            # list_sessions() forwards raw persisted metadata; an unusable value
            # must not escape the idle scan and stop the agent loop.
            return False
        return idle_seconds >= self._ttl * 60
    def check_expired(
        self,
        schedule_background: Callable[[Coroutine[Any, Any, None]], None],
        resolve_runtime: Callable[[Session], LLMRuntime],
        active_session_keys: Collection[str] = (),
    ) -> None:
        """Schedule archival for idle sessions, skipping those with in-flight agent tasks."""
        now = datetime.now()
        for info in self.sessions.list_sessions():
            key = info.get("key", "")
            if not key or self._is_internal_session(key) or key in self._archiving:
                continue
            if key in active_session_keys:
                continue
            updated_at = info.get("updated_at")
            if self._is_expired(updated_at, now) and self._has_unarchived_messages(key):
                session = self.sessions.get_or_create(key)
                try:
                    runtime = resolve_runtime(session)
                except (KeyError, ValueError):
                    # Invalid session selections remain recoverable through /model.
                    continue
                self._archiving.add(key)
                schedule_background(self._archive(key, runtime=runtime))

check_expired 会跳过三类 session：dream: 前缀的内部会话、 正在归档中的（_archiving 集合）、以及有活跃 agent task 的（active_session_keys 来自 _pending_queues.keys()）。 配置项 idleCompactAfterMinutes 默认 15 分钟（schema.py:150-155）， 设 0 禁用。

十、练习

基础会话 JSONL 默认 save(fsync=False)，关机时才 flush_all(fsync=True)。如果进程被 kill -9 强杀，可能丢失什么？为什么日常热路径不强制 fsync？

可能丢失：最后一次 save() 写入的数据——通常是当前回合尚未 fsync 的消息和 metadata 更新。

因为 fsync 是同步磁盘 IO，每个回合可能写盘 2-3 次（早持久化用户消息、 save 阶段、压缩后更新 last_consolidated），每次都 fsync 会把 save 阶段 latency 从毫秒级拉到 tens of ms。

设计取舍：正常运行容忍最后一秒的丢失，优雅关机补齐耐久性。 源码位置：manager.py:728（fsync 参数）和 manager.py:1134-1150（flush_all）。

进阶某会话 last_consolidated = 100，messages 共 150 条。 调用 get_history(max_messages=20) 时，实际回放从哪条开始？为什么不是从第 130 条？

不是简单从 130 开始。流程如下：

  1. replay_start = min(100, recent_start)，其中 recent_start 至少保留尾部 8 条（MIN_COMPACTED_REPLAY_MESSAGES），所以 replay_start 可能是 142。
  2. replayable = messages[142:]，共 8 条未归档 + 可能更多已归档后缀。
  3. recent_message_start_index(replayable, 20, extend_to_user=...) 从尾部数 20 条，并回溯到起始 user 消息。
  4. find_legal_message_start 清理孤立 tool result。

关键：last_consolidated 是归档指针，不是"从这儿开始回放"。 即使消息 0-99 已归档进 history.jsonl，文件里它们仍在——只是 get_history() 跳过。 源码：manager.py:197-250。

挑战假设 Consolidator 在 assistant 消息的 tool result 还没回填时就切了边界（绕过了 pick_consolidation_boundary）。描述一条具体的非法消息序列，以及 API 会返回什么错误。

非法序列示例：

[0] user: "查一下天气" [1] assistant: { tool_calls: [{ id: "call_1", name: "web_search", ... }] } [2] tool: { tool_call_id: "call_1", content: "..." } ← 被归档切掉 [3] assistant: "今天上海晴..." ← 留在 replay 里

归档后 get_history() 可能从 [3] 开始—— 但 [3] 前面缺少 [1] 的 tool result [2]，消息序列不完整。 OpenAI API 典型报错：400 Invalid parameter: messages with role 'tool' must be a response to a preceding message with 'tool_calls'， 或 Anthropic 的 tool_use blocks must be followed by tool_result blocks。

这正是 pick_consolidation_boundary（memory.py:838-858） 只在 role == "user" 处切的原因——user 消息是自然回合边界， 其前的 assistant/tool 序列已经闭合。

本章小结

记忆 = 三层存储（JSONL 会话 / history 归档 / Markdown 长期知识）+ 原子写入（tmp + replace + fsync）+ 指针式压缩（last_consolidated + 最小回放后缀）+ Dream 两阶段整合。 下一章进入边缘层：18 个聊天平台如何通过渠道适配层接入 第 02 章 的消息总线。
