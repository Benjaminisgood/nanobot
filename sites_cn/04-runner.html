第 04 章 · 核心链路

04 AgentRunner：ReAct 循环

1670 行，全项目 ReAct（Reason + Act，推理—行动）循环的唯一实现。 第 03 章的 AgentLoop 负责"什么时候、以什么上下文"启动一轮对话； 这一章我们读 AgentRunner——它只认 AgentRunSpec， 在消息列表上反复"问模型 → 执行工具 → 回填结果"，直到给出最终答案或触达终止条件。

一、职责边界：AgentRunner 做什么、不做什么

类的 docstring 只有一句话，但边界非常清晰：

class AgentRunner:
    """Run a tool-capable LLM loop without product-layer concerns."""

翻译过来：跑一个能调工具的 LLM 循环，但不碰产品层的事。 它不知道 Telegram 还是 WebUI，不知道会话 JSONL 存在哪， 也不知道用户按了 /stop 之后该怎么恢复检查点—— 那些全是 AgentLoop（第 03 章）和 Session 持久化（第 07 章）的职责。

◆ 核心要点：Runner 的唯一输入是 AgentRunSpec

AgentLoop._run_turn() 在 build 阶段拼好 initial_messages、工具注册表、运行时配置， 然后构造一个 AgentRunSpec 交给 runner.run(spec)。 Runner 返回 AgentRunResult，Loop 再在 save 阶段 把 result.messages 里新增的部分写盘。

这条边界的好处是：CLI、OpenAI 兼容 API、subagent _spawn 工具 都可以复用同一个 Runner，而不必复制 ReAct 逻辑。

二、AgentRunSpec 与 AgentRunResult：两个契约

为什么不把 20 个参数直接传给 run()？ 因为 ReAct 循环的配置项会随功能增长——注入回调、检查点、持续目标、 provider 续传状态……用一个大 dataclass 集中声明， 调用方只填自己关心的字段，其余走默认值。 两个类都加了 @dataclass(slots=True)： 固定字段布局、禁止动态增属性，内存更紧凑，也防止 typo 写成不存在的字段。 

@dataclass(slots=True)

    initial_messages: list[dict[str, Any]]

    runtime: LLMRuntime

    max_tool_result_chars: int

重要字段速查

字段类型 / 默认作用
max_iterations int（必填） ReAct 主循环上限。每次迭代 = 一次 LLM 请求（含可能的工具执行）。耗尽时走 stop_reason="max_iterations"。
concurrent_tools bool，默认 False 为真时，同一批 concurrency_safe 工具用 asyncio.gather 并行执行。
fail_on_tool_error bool，默认 False 为真时工具失败会返回 fatal_error，整轮以 tool_error 终止；默认把错误文本喂回模型让它自救。
injection_callback 可选回调 由 Loop 注入 _drain_pending，在工具序列闭合后的安全点取出用户追加消息（见第 03 章第六节）。
checkpoint_callback 可选回调 在 awaiting_tools / tools_completed / final_response 等阶段持久化中间状态，供 /stop 恢复。
goal_active_predicate Callable[[], bool] | None 持续目标（sustained goal）是否仍活跃；与 goal_continue_message 配合实现自动续跑。
provider_state ProviderConversationState | None 跨轮 provider 续传状态（如 OpenAI Responses API 的 response_id），由 Loop 在 build 阶段注入。
llm_timeout_s float | None 单次 LLM 请求超时（秒），None 表示不限。
finalize_on_max_iterations bool，默认 True 迭代用尽时是否再发起一次不带工具的 LLM 请求，让模型给出总结而非模板兜底。
? 为什么 spec 和 result 分开

AgentRunSpec 是输入契约——只读配置，Runner 不应修改它。 AgentRunResult 是输出契约——包含可能被 append 了数十条 assistant/tool 消息的完整 messages 列表，以及 stop_reason、 token 用量、流式尾部等运行时产物。

Loop 拿到 result 后，用 initial_messages 的长度和 result.messages 做差， 只持久化新增部分。如果把输入输出揉成一个对象，这个"append 边界"就很难保持清晰。

三、run()：钩子生命周期与四段式异常处理

run() 是 Runner 对外的唯一入口。它做三件事： 复制一份 initial_messages 作为可变工作副本； 包一层 hook 生命周期； 把核心逻辑委托给 _run_core()。 

    async def run(self, spec: AgentRunSpec) -> AgentRunResult:
        hook = spec.hook or AgentHook()
        messages = list(spec.initial_messages)
        context = AgentRunHookContext(messages=deepcopy(messages))

        try:
            await hook.before_run(context)
            result = await self._run_core(spec, hook, messages)
        except asyncio.CancelledError as exc:
            context.messages = deepcopy(messages)
            context.stop_reason = "cancelled"
            context.error = None
            context.exception = exc
            raise
        except Exception as exc:
            context.messages = deepcopy(messages)
            context.stop_reason = "error"
            context.error = f"Error: {type(exc).__name__}: {exc}"
            context.exception = exc
            await hook.on_error(context)
            raise
        else:
            context.messages = deepcopy(result.messages)
            context.final_content = result.final_content
            context.tools_used = list(result.tools_used)
            context.usage = dict(result.usage)
            context.stop_reason = result.stop_reason
            context.error = result.error
            context.tool_events = deepcopy(result.tool_events)
            context.had_injections = result.had_injections
            context.exception = None
            if context.error is not None:
                await hook.on_error(context)
            await hook.after_run(context)
            return result
        finally:
            context.messages = deepcopy(messages)
            if context.exception is None:
                await hook.on_finally(context)
            else:
                try:
                    await hook.on_finally(context)
                except Exception:
                    logger.exception(
                        "AgentHook.on_finally error after {}",
                        context.stop_reason or "run exception",
                    )

四个分支各管一类结局：

分支触发条件行为
except CancelledError 用户 /stop、任务被取消 更新 context 为 cancelled，直接 raise，不调 on_error。取消不是"错误"。
except Exception 未预期的运行时异常 调 on_error，再 raise 把异常传给 Loop。
else _run_core 正常返回 若 result 带 error（如 LLM 返回 finish_reason=error）也调 on_error；然后 after_run 并返回 result。
finally 无论成败 总是调 on_finally——但异常路径下再套一层 try/except。
▲ 易错点：finally 里为什么要再套 try

设想 _run_core 抛了 RuntimeError("provider down")， except Exception 已经记录了原始异常并准备 raise。 如果 on_finally 里又抛了 KeyError， 没有内层 try 的话，最终冒泡的是 KeyError，原始 RuntimeError 被覆盖—— 调试时完全误导。

内层只记日志、不 re-raise，保证"第一个异常"始终是真相。 正常路径（context.exception is None）则不需要这层保护。

四、_run_core()：ReAct 主循环

主循环的结构就是一个 for iteration in range(spec.max_iterations)。 每次迭代：治理上下文 → 调模型 → 观察响应 → 分支（执行工具 / 收尾回答）。

4.1 两份历史：持久化 vs 送给模型

循环开头这段注释是理解 Runner 与 Memory 分工的关键：

        for iteration in range(spec.max_iterations):
            # Keep the persisted conversation untouched. Context governance
            # may repair or compact historical messages for the model, but
            # those synthetic edits must not shift the append boundary used
            # later when the caller saves only the new turn. A governance
            # failure must stop the run instead of sending an ungoverned copy.
            messages_for_model = self.context_governor.prepare_for_model(
                governance_config,
                messages,
                compacted_tool_call_ids,
            )
            context = AgentHookContext(
                iteration=iteration,
                messages=messages,
                session_key=spec.session_key,
            )
            await hook.before_iteration(context)
            provider_context = conversation_state.prepare_request(
                messages,
                context_window_tokens=spec.runtime.context_window_tokens,
                model_messages=messages_for_model,
            )
            response = await self._request_model(
                spec,
                messages_for_model,
                hook,
                context,
                conversation_state=conversation_state,
                provider_context=provider_context,
            )
            conversation_state.observe_response(response, messages)
◆ 核心要点：messages 与 messages_for_model

messages 是权威 transcript——所有 append 都发生在这里， Loop 最终拿它去持久化。 messages_for_model 是治理后的副本——可能被压缩、 截断工具结果、修复非法角色交替，只用于本次 API 请求。

如果不分离，一次 context 压缩就会改写持久化边界， 下次读会话历史会看到"被合成过的"消息——用户和 Consolidator 都会困惑。 注释还强调：治理失败必须中止运行，不能悄悄 fallback 到未治理副本 （那会绕过 token 预算和安全截断）。

4.2 工具分支：should_execute_tools 门控

模型返回后，Runner 先看 response.should_execute_tools， 而不是裸看 has_tool_calls： 

    @property
    def should_execute_tools(self) -> bool:
        """Tools execute only when has_tool_calls AND finish_reason is a tool-capable stop.
        Blocks gateway-injected calls under ``refusal`` / ``content_filter`` / ``error`` (#3220)."""
        if not self.has_tool_calls:
            return False
        return self.finish_reason in ("tool_calls", "function_call", "stop")

门控通过后，工具分支的时序如下：

should_execute_tools == True → build_assistant_message + append 到 messages → _emit_checkpoint(phase="awaiting_tools") → _execute_tools → 每个结果 append 为 role="tool" 消息 → _emit_checkpoint(phase="tools_completed") → _try_drain_injections（工具序列已闭合，安全注入点） → continue 下一轮迭代
            if response.should_execute_tools:
                context.tool_calls = list(response.tool_calls)
                if hook.wants_streaming():
                    await hook.on_stream_end(context, resuming=True)

                assistant_message = build_assistant_message(
                    response.content or "",
                    tool_calls=[tc.to_openai_tool_call() for tc in response.tool_calls],
                    reasoning_content=response.reasoning_content,
                    thinking_blocks=response.thinking_blocks,
                )
                assistant_message = conversation_state.project_response_message(
                    assistant_message,
                    response,
                )
                messages.append(assistant_message)
                await self._emit_checkpoint(
                    spec,
                    {
                        "phase": "awaiting_tools",
                        "iteration": iteration,
                        "model": spec.runtime.model,
                        "assistant_message": assistant_message,
                        "completed_tool_results": [],
                        "pending_tool_calls": [tc.to_openai_tool_call() for tc in response.tool_calls],
                    },
                )

                await hook.before_execute_tools(context)

                results, new_events, fatal_error = await self._execute_tools(
                    spec,
                    response.tool_calls,
                    external_lookup_counts,
                    workspace_violation_counts,
                    hook,
                    context,
                )

如果模型带了 tool_calls 但 finish_reason 不对（比如 content filter 或 refusal）， Runner 只打 warning、不执行工具——避免在模型已拒绝的场景下误跑副作用操作： 

            if response.has_tool_calls:
                logger.warning(
                    "Ignoring tool calls under finish_reason='{}' for {}",
                    response.finish_reason,
                    spec.session_key or "default",
                )
? 为什么 finish_reason 也要检查

部分 gateway 在 content filter 或 refusal 时仍会在响应体里塞 tool_calls 字段 （可能是截断前的中间态，或 provider bug）。 如果只看 has_tool_calls，agent 会在模型"已经拒绝回答"的情况下 照样执行 exec、写文件——安全与语义都不对。

should_execute_tools 把"有调用"和"该执行"拆成两步， 是 provider 层（第 05 章）和 runner 层之间的明确契约。

4.3 无工具时的收尾：finalize 与空回复重试

不走工具分支时，Runner 调 hook.finalize_content() 做渠道特定的内容清洗， 然后处理空回复——最多重试 _MAX_EMPTY_RETRIES（值为 2）次， 仍空则走 _request_finalization_retry 再要一次不带工具的总结。

正常结束时 append assistant 消息、发 final_response 检查点、 break 跳出循环。若 fatal_error 来自工具且 fail_on_tool_error=True，则 stop_reason="tool_error" 提前 break。

五、_execute_tools 与并发分批

一次 LLM 响应可能包含多个 tool call。Runner 不会无脑 gather 全部—— 先按工具的安全属性分批： 

    @property
    def read_only(self) -> bool:
        """Whether this tool is side-effect free and safe to parallelize."""
        return False

    @property
    def concurrency_safe(self) -> bool:
        """Whether this tool can run alongside other concurrency-safe tools."""
        return self.read_only and not self.exclusive

    @property
    def exclusive(self) -> bool:
        """Whether this tool should run alone even if concurrency is enabled."""
        return False

三个属性的关系：

  • read_only：无副作用，理论上可并行（如 read_file、web_search）。
  • exclusive：即使只读也必须独占（如 exec 工具返回 True，见 第 06 章）。
  • concurrency_safe：read_only and not exclusive——分批算法的唯一判据。
    def _partition_tool_batches(
        self,
        spec: AgentRunSpec,
        tool_calls: list[ToolCallRequest],
    ) -> list[list[ToolCallRequest]]:
        if not spec.concurrent_tools:
            return [[tool_call] for tool_call in tool_calls]

        batches: list[list[ToolCallRequest]] = []
        current: list[ToolCallRequest] = []
        for tool_call in tool_calls:
            get_tool = cast(Callable[[str], Any] | None, getattr(spec.tools, "get", None))
            tool = get_tool(tool_call.name) if callable(get_tool) else None
            can_batch = bool(tool and tool.concurrency_safe)
            if can_batch:
                current.append(tool_call)
                continue
            if current:
                batches.append(current)
                current = []
            batches.append([tool_call])
        if current:
            batches.append(current)
        return batches
    async def _execute_tools(
        self,
        spec: AgentRunSpec,
        tool_calls: list[ToolCallRequest],
        external_lookup_counts: dict[str, int],
        workspace_violation_counts: dict[str, int],
        hook: AgentHook | None = None,
        context: AgentHookContext | None = None,
    ) -> tuple[list[Any], list[dict[str, str]], BaseException | None]:
        hook = hook or AgentHook()
        context = context or AgentHookContext(iteration=0, messages=[])
        batches = self._partition_tool_batches(spec, tool_calls)
        tool_results: list[tuple[Any, dict[str, str], BaseException | None]] = []
        for batch in batches:
            if spec.concurrent_tools and len(batch) > 1:
                batch_results = await asyncio.gather(*(
                    self._run_tool(
                        spec,
                        tool_call,
                        external_lookup_counts,
                        workspace_violation_counts,
                        hook,
                        context,
                    )
                    for tool_call in batch
                ))
                tool_results.extend(batch_results)
            else:
                batch_results: list[tuple[Any, dict[str, str], BaseException | None]] = []
                for tool_call in batch:
                    result = await self._run_tool(
                        spec,
                        tool_call,
                        external_lookup_counts,
                        workspace_violation_counts,
                        hook,
                        context,
                    )
                    tool_results.append(result)
                    batch_results.append(result)

        results: list[Any] = []
        events: list[dict[str, str]] = []
        fatal_error: BaseException | None = None
        for result, event, error in tool_results:
            results.append(result)
            events.append(event)
            if error is not None and fatal_error is None:
                fatal_error = error
        return results, events, fatal_error
✓ 实用提示

并发需要两个条件同时满足：spec.concurrent_tools=True 且当前 batch 里多于一个调用。 单个 concurrency_safe 工具仍然串行——避免为 batch size 1 付 gather 的开销。 写新工具时：只读且无副作用 → read_only=True； 会改状态或占全局资源 → 保持默认或设 exclusive=True。

六、_run_tool：错误分层与"喂回模型"

单个工具的执行是 ReAct 循环里最复杂的边界—— 它要在安全、可恢复性和 fail_on_tool_error 之间做分层决策。 

    async def _run_tool(
        self,
        spec: AgentRunSpec,
        tool_call: ToolCallRequest,
        external_lookup_counts: dict[str, int],
        workspace_violation_counts: dict[str, int],
        hook: AgentHook | None = None,
        context: AgentHookContext | None = None,
    ) -> tuple[Any, dict[str, str], BaseException | None]:
        hook = hook or AgentHook()
        context = context or AgentHookContext(iteration=0, messages=[])
        hint = "\n\n[Analyze the error above and try a different approach.]"
        lookup_error = repeated_external_lookup_error(
            tool_call.name,
            tool_call.arguments,
            external_lookup_counts,
        )
        if lookup_error:
            event = {
                "name": tool_call.name,
                "status": "error",
                "detail": "repeated external lookup blocked",
            }
            if spec.fail_on_tool_error:
                return lookup_error + hint, event, RuntimeError(lookup_error)
            return lookup_error + hint, event, None
        prepare_call = cast(
            Callable[[str, Any], object] | None,
            getattr(spec.tools, "prepare_call", None),
        )
        tool, params, prep_error = None, tool_call.arguments, None
        if callable(prepare_call):
            prepared = prepare_call(tool_call.name, tool_call.arguments)
            if isinstance(prepared, tuple):
                prepared_tuple = cast(tuple[object, ...], prepared)
                if len(prepared_tuple) == 3:
                    tool, params, prep_error = cast(tuple[Any, Any, str | None], prepared_tuple)
        if prep_error:
            event = {
                "name": tool_call.name,
                "status": "error",
                "detail": prep_error.split(": ", 1)[-1][:120],
            }
            handled = self._classify_violation(
                raw_text=prep_error,
                soft_payload=prep_error + hint,
                event=event,
                tool_call=tool_call,
                workspace_violation_counts=workspace_violation_counts,
            )
            if handled is not None:
                return handled
            return prep_error + hint, event, (
                RuntimeError(prep_error) if spec.fail_on_tool_error else None
            )
        await hook.before_execute_tool(context, tool_call, tool, params)
        try:
            if tool is not None:
                result = await tool.execute(**params)
            else:
                result = await spec.tools.execute(tool_call.name, params)
        except asyncio.CancelledError:
            raise
        except Exception as exc:
            await hook.on_execute_tool_error(context, tool_call, tool, params, exc)
            event = {
                "name": tool_call.name,
                "status": "error",
                "detail": str(exc),
            }
            payload = f"Error: {type(exc).__name__}: {exc}"
            handled = self._classify_violation(
                raw_text=str(exc),
                # Preserve legacy exception payloads without the retry hint.
                soft_payload=payload,
                event=event,
                tool_call=tool_call,
                workspace_violation_counts=workspace_violation_counts,
            )
            if handled is not None:
                return handled
            if spec.fail_on_tool_error:
                return payload, event, exc
            return payload, event, None

错误处理的优先级链：

  1. 重复外部查询拦截——同一 URL/目标短时间内反复 web_fetch，直接返回文本，不真正调用。
  2. prepare_call 三元组——(tool, params, prep_error) 在参数校验阶段就能失败（路径非法、JSON 解析错误等）。
  3. _classify_violation——区分 SSRF 硬边界 vs 工作区软违规，决定是否升级提示。
  4. 执行期异常 / 工具返回的错误字符串——默认变成 tool 消息的 content，附带 hint 常量引导模型换思路。
    def _classify_violation(
        self,
        *,
        raw_text: str,
        soft_payload: str,
        event: dict[str, str],
        tool_call: ToolCallRequest,
        workspace_violation_counts: dict[str, int],
    ) -> tuple[Any, dict[str, str], BaseException | None] | None:
        """Classify safety-boundary failures, or return ``None`` to pass through."""
        if self._is_ssrf_violation(raw_text):
            logger.warning(
                "Tool {} blocked by SSRF guard; returning non-retryable tool error: {}",
                tool_call.name,
                raw_text.replace("\n", " ").strip()[:200],
            )
            event["detail"] = self._event_detail("ssrf_violation: ", raw_text)
            return self._ssrf_soft_payload(raw_text), event, None

        if self._is_workspace_violation(raw_text):
            escalation = repeated_workspace_violation_error(
                tool_call.name,
                tool_call.arguments,
                workspace_violation_counts,
            )
            event["detail"] = self._event_detail("workspace_violation: ", raw_text)
            if escalation is not None:
                logger.warning(
                    "Tool {} hit workspace boundary repeatedly; escalating hint",
                    tool_call.name,
                )
                event["detail"] = self._event_detail(
                    "workspace_violation_escalated: ",
                    raw_text,
                )
                return escalation, event, None
            return soft_payload, event, None

        return None
◆ 核心要点：工具错误默认不抛异常

返回值三元组 (result_text, event, fatal_error) 里， 只有第三个元素非 None 时整轮才会以 tool_error 终止。 默认路径：fatal_error=None，错误文本作为 role="tool" 消息 append 到 messages，下一轮 LLM 自己读错误、自己改策略。

这是 ReAct 范式的核心——模型是控制流，Runner 是执行器。 如果每次工具失败都抛异常终止，一个 typo 参数就会让整个回合崩溃； 把错误当观测（observation）喂回去，agent 才能"读了报错再试另一种写法"。 SSRF 是例外：返回带 _SSRF_BOUNDARY_NOTE 的不可绕过提示（见 第 10 章），但仍不抛 fatal——对话可以继续，只是模型不应再试。

七、终止条件汇总

stop_reason触发点典型后果
completed 模型给出最终文本回复，无待执行工具，正常 break final_content 为 assistant 回复；messages 含完整 transcript
max_iterations for 循环走完 else 分支（runner.py:828） 可选 finalization 请求 + 模板兜底消息
tool_error _execute_tools 返回 fatal_error 且 fail_on_tool_error=True 整轮中止，error 字段有描述
error LLM finish_reason=="error"，或 run() 捕获未处理异常 用户看到 error_message；transcript 可能写入占位 assistant 消息
cancelled run() 的 CancelledError 分支（不返回 result，直接 raise） Loop 负责检查点恢复（第 03 章 3.2 节）
empty_final_response 多次空回复且 finalization 仍失败 写入 EMPTY_FINAL_RESPONSE_MESSAGE

迭代用尽时的 finalization

当 ReAct 循环跑满 max_iterations 还没自然结束时， 若 finalize_on_max_iterations=True（默认），Runner 会再发起一次 不带工具 的 LLM 请求，让模型基于已有 transcript 给出总结： 

    async def _try_finalize_after_max_iterations(
        self,
        spec: AgentRunSpec,
        hook: AgentHook,
        messages: list[dict[str, Any]],
        usage: dict[str, int],
        conversation_state: ProviderConversationStateController,
    ) -> str | None:
        retry_messages = self._budget_exhausted_finalization_messages(messages)
        try:
            response = await self._request_no_tools(
                spec,
                retry_messages,
                provider_context=conversation_state.independent_request_context(
                    context_window_tokens=spec.runtime.context_window_tokens,
                ),
            )
        except Exception:
            logger.exception(
                "Budget-exhausted finalization failed for {}; using fallback",
                spec.session_key or "default",
            )
            return None

        raw_usage = self._usage_or_estimate(spec, retry_messages, response)
        self._accumulate_usage(usage, raw_usage)
        if response.finish_reason == "error" or response.has_tool_calls:
            logger.warning(
                "Budget-exhausted finalization returned finish_reason='{}' "
                "with {} tool call(s) for {}; using fallback",
                response.finish_reason,
                len(response.tool_calls),
                spec.session_key or "default",
            )
            return None

        context = AgentHookContext(
            iteration=spec.max_iterations,
            messages=messages,
            response=response,
            usage=dict(raw_usage),
            session_key=spec.session_key,
        )
        clean = hook.finalize_content(context, response.content)
        if is_blank_text(clean):
            return None
        return clean
    async def _request_no_tools(
        self,
        spec: AgentRunSpec,
        messages: list[dict[str, Any]],
        *,
        provider_context: ProviderCallContext | None = None,
    ) -> LLMResponse:
        kwargs = self._build_request_kwargs(
            spec,
            messages,
            tools=None,
        )
        return await spec.runtime.provider.chat_with_retry(
            **kwargs,
            provider_context=provider_context,
        )
? 为什么 max_iterations 还要再问一次

迭代用尽往往意味着 agent 还在 tool loop 里打转——此时 transcript 里已经有大量 工具结果和部分推理，只是没来得及输出面向用户的总结。 直接返回模板"已达到最大迭代次数"会让用户空手而归。

_request_no_tools 显式传 tools=None， 防止 finalization 回合又触发工具调用（若仍返回 tool_calls 则 fallback 到模板）。 这是"尽力交付"而不是"静默失败"的设计。

八、持续目标（sustained goal）的续跑

某些长任务需要 agent 在"模型以为已经答完"之后继续工作。 Runner 通过 goal_active_predicate 和 goal_continue_message 在最终回复路径上注入一条 synthetic user 消息，迫使下一轮迭代继续： 

    def _build_goal_continue_message(self, spec: AgentRunSpec) -> dict[str, str]:
        custom = spec.goal_continue_message
        if callable(custom):
            try:
                custom = custom()
            except Exception:
                logger.exception("goal_continue_message callback failed")
                custom = None
        return build_goal_continue_message(custom)

触发点在 _try_drain_injections：当没有真实用户注入、但 allow_goal_continue=True 且 predicate 返回真时， 构造 goal continue 消息 append 到 messages 并 continue 循环。 Loop 层负责维护 predicate（读 session goal state），Runner 只负责"收到继续信号就再跑一轮"。

▲ 易错点：goal continue 与 injection 共用配额

真实注入走 injection_callback，受 _MAX_INJECTION_CYCLES（5）限制； goal continue 不计入 injection_cycles，但在 finish_reason in {refusal, content_filter} 时会被禁用—— 模型已明确拒绝时不应强行续跑。

续跑前若已有 assistant_message，会先 append 并打 final_response 检查点，保证中途停止时 partial 答案不丢。

九、练习

基础模型返回了 3 个 tool_calls，finish_reason="content_filter"。Runner 会执行这些工具吗？为什么？

  • A 会，因为有 tool_calls
  • B 不会，should_execute_tools 为 False
  • C 会，但只执行 read_only 工具

答案：B。

should_execute_tools 要求 finish_reason in ("tool_calls", "function_call", "stop")。 content_filter 不在其中，因此整个工具分支被跳过。 若 has_tool_calls 仍为真，会打 warning（runner.py:625）后忽略。

后果：若错误地只看 has_tool_calls 就执行， agent 可能在内容已被平台过滤的场景下仍运行 write_file 或 exec—— 既违反 provider 语义，也可能产生用户未授权的副作用。

进阶concurrent_tools=True，模型一次返回 4 个调用：read_file(a)、read_file(b)、exec(cmd)、web_search(q)。描述 _partition_tool_batches 的分批结果和执行时序。

分批结果（3 个 batch）：

Batch 1（并发 gather）: read_file(a), read_file(b), web_search(q) — 三者 read_only 且非 exclusive → concurrency_safe Batch 2（串行）: exec(cmd) — exclusive=True，flush 掉前面积累的 batch 后单独成批

执行时序：

  1. Batch 1 三个工具 asyncio.gather 并行，各自走完整 _run_tool 流程。
  2. Batch 2 的 exec 单独 await，不会与任何工具重叠。
  3. 四个结果按原始 tool_calls 顺序 zip 回 tool 消息（gather 保序）。

若 exec 和 write_file 被放进同一 batch 并行， 可能出现 shell 读到半写入的文件——这就是 exclusive 存在的原因。

挑战fail_on_tool_error=False（默认）时，read_file 因路径越界返回 workspace violation 文本。请构造从工具失败到模型可能纠正的完整消息时序，并说明若改成 fail_on_tool_error=True 时序如何变化。

默认路径时序：

iter 0 LLM → tool_calls: read_file("/etc/passwd") Runner append assistant (含 tool_calls) _run_tool → prepare_call 或 execute 返回 violation 文本 _classify_violation → soft_payload + hint append 为 role="tool" fatal_error=None → 不 break checkpoint tools_completed → continue iter 1 LLM 读到 tool 消息里的 "outside the configured workspace" + "[Analyze the error above and try a different approach.]" → 可能改调 read_file("./workspace/...") 或 ask user

关键点：错误从未抛到 run() 的 except Exception； transcript 里保留了完整的 assistant→tool 对，模型在下一轮有完整观测。

fail_on_tool_error=True 时：

iter 0 同上，但 _run_tool 返回 fatal_error=RuntimeError(violation) _execute_tools 汇总 fatal_error stop_reason="tool_error"，append 错误 final_content，break 不会进入 iter 1

用户看到硬错误而非 agent 自救。此模式适合测试/CI 或需要严格失败语义的 API 调用方。 生产对话默认 False，因为大多数参数错误都值得给模型一次纠正机会。

本章小结

AgentRunner = AgentRunSpec 契约 + ReAct 主循环（治理副本 / 权威 transcript 分离）+ 工具并发分批与错误喂回 + 多路径终止与 max_iterations finalization。 它刻意不碰渠道和持久化，所以读源码时始终问一个问题： "这段逻辑该在 Runner 里，还是该在 Loop 传给 spec 的回调里？"
