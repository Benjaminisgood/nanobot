架构总览与数据流

这一章不看具体实现，只做一件事：建立一张能装进脑子的地图。 读完你应该能回答——一条用户消息从进入进程到发出回复，一共经过哪几个所有权边界？

一、五层结构与依赖方向

nanobot 的目录不是按"功能"划分的，而是按依赖方向划分的。理解这一点，你就知道该往哪个目录找代码：

◆ 核心要点

渠道不知道 agent 的存在，agent 也不知道渠道的存在。 它们之间唯一的接触面是 bus/events.py 里的两个 dataclass。 这就是为什么这个项目能支持 18 个聊天平台，而 loop.py 里几乎没有任何平台专属代码。

二、一条消息的完整旅程

这是全站最重要的一张图。下面每一步都标注了真实的文件与函数名，你可以按顺序在编辑器里逐个跳转验证。

1
平台 SDK 收到消息 以 Telegram 为例：python-telegram-bot 的 MessageHandler 触发 TelegramChannel._on_message，随后进入 _process_message_update， 在这里把 text、caption、location、下载好的媒体文件路径拼成统一的 content 字符串。
↓
2
规范化 + 鉴权 → 发布到总线 所有渠道最终都调用基类的 BaseChannel._handle_message()。 它先做发送者鉴权（不在白名单的私聊会收到配对码），再构造 InboundMessage， 最后 await self.bus.publish_inbound(msg)。
↓
3
AgentLoop.run() 取出消息并做路由决策 核心调度循环。取到消息后依次判断：是否运行时控制指令？是否优先命令（如 /stop）？ 是否要延后自动化回合？该会话是否已有任务在跑（则塞进注入队列）？都不是才 asyncio.create_task(self._dispatch(msg))。
↓
4
_dispatch()：按会话串行、跨会话并发 拿到该 session 的 asyncio.Lock 和全局并发闸门，创建 maxsize=20 的注入队列，然后调用 _process_message()。
↓
5
_process_message()：七阶段流水线 restore → compact → command → build → run → save → respond。 所有中间状态都挂在一个 TurnContext 数据类上传递。
↓
6
AgentRunner.run()：真正的 ReAct 循环 build 阶段装配好 initial_messages 后，run 阶段把它包装成 AgentRunSpec 交给 runner。runner 在 for iteration in range(max_iterations) 里反复：调 LLM → 有工具调用就执行 → 结果回填 → 再调 LLM。
↓
7
持久化 + 组装回复 save 阶段把新增消息原子写入会话 JSONL；respond 阶段把最终文本装成 OutboundMessage。
↓
8
回到渠道 TurnDelivery.complete() 调 bus.publish_outbound(response)； ChannelManager._dispatch_outbound() 这个常驻任务取出消息， 按 msg.channel 找到对应渠道，调用它的 send()（带指数退避重试）。

四、并发模型：谁和谁能并行

这是初读时最容易搞混的部分。nanobot 有四个层次的并发，边界各不相同：

层次粒度机制
渠道之间完全并行每个渠道一个 asyncio.Task，由 ChannelManager.start_all() 启动
会话之间并行（受闸门限制）_dispatch() 里每个 session 一把 asyncio.Lock，外加一个全局 _concurrency_gate
同一会话内严格串行同一把会话锁。后来的消息不会新建任务，而是塞进 _pending_queues 做"回合中注入"
同一轮的工具条件并行_partition_tool_batches() 按 concurrency_safe / exclusive 分批，安全的批用 asyncio.gather
▲ 易错点

"同一会话严格串行"不等于"后来的消息被丢弃"。看 loop.py:1214 附近： 如果该会话已有活跃的 pending 队列，消息会被 put_nowait 进去， 在当轮的工具执行间隙被 _try_drain_injections 取出并插入到正在进行的对话中。 这就是"你在 agent 干活时追加一句话，它能立刻反应"的实现原理。

而且注意 _dispatch() 的 finally 块（loop.py:1346 起）： 回合结束时队列里的残留消息会被重新 publish 回 inbound 总线，而不是静默丢失。

五、为什么这个项目值得读

在读具体代码前，先记住三个"它做对了但很多项目做错了"的地方，这样你在后面几章看到时会更有感觉：

? 为什么这样设计

1. 宁可重复，也不过早抽象。 .agent/design.md 明确写着：渠道和 provider 允许 重复相似逻辑（发送重试、媒体处理、消息切分）， 不要为了消除重复而引入复杂基类。每个渠道文件必须能独立阅读。 这是为什么 feishu/runtime.py 有 2887 行却仍然可维护——你读它时不需要同时理解另外 17 个渠道。

2. 动态边界在边缘处做类型化。 wire payload、持久化记录、第三方 SDK 对象都被视为不可信的动态边界， 要在所属边缘用 parser 或 normalizer 处理一次，内部代码只接收具体类型。 typing.cast 不做运行时校验，因此每个新 cast 都必须有同路径的运行时检查支撑。

3. 显式优于魔法。 配置必须在 config/schema.py 的 Pydantic 模型里显式声明； 错误处理应该抛出清晰异常而不是静默纠正坏输入；provider 自动探测存在， 但每条解析路径都必须能从 factory 追踪到具体 provider 类。

六、练习

基础如果你要新增一个"短信"渠道，需要修改 agent/loop.py 吗？为什么？

不需要。

根据 .agent/design.md 的第一条约束，新能力应该在边缘添加。 具体做法是在 nanobot/channels/ 下新建一个自包含的包（例如 sms/）， 包含 manifest.py（声明 PLUGIN: ChannelPlugin）和 runtime.py （继承 BaseChannel，实现 start / stop / send 三个抽象方法）。

ChannelManager._init_channels() 会通过 pkgutil.iter_modules() 自动发现它，无需在任何地方注册。 核心层永远只看到 InboundMessage，它完全不关心这条消息来自短信还是 Telegram。

细节见第 08 章。

进阶用户在 agent 正在执行一个长任务（比如跑测试）时又发了一条消息。系统有三种可能的处理方式，nanobot 选了哪一种？在哪一行代码里决定的？

  • A 新建一个并发任务，两条消息同时处理
  • B 丢弃新消息，提示"忙碌中"
  • C 放入队列，在当轮的执行间隙注入到正在进行的对话里

答案：C。

决策点在 AgentLoop.run() 的调度循环里：

                if effective_key in self._pending_queues:
                    # Non-priority commands must not be queued for injection;
                    # dispatch them directly (same pattern as priority commands).
                    if self.commands.is_dispatchable_command(raw):
                        await self._dispatch_command_inline(
                            msg, effective_key, raw,
                            self.commands.dispatch,
                        )
                        continue

self._pending_queues 只有持有会话锁的那个任务才会注册（见 loop.py:1265 附近的注释："Only the task that owns the session lock may publish the active mid-turn injection queue for this session"）。所以 effective_key in self._pending_queues 成立，就等价于"这个会话正在被处理中"。

注意这里还有一个分支：非优先级的斜杠命令不能进注入队列， 而要直接 inline 分发。否则你在 agent 干活时敲 /model， 这条命令会被当成对话内容喂给 LLM，而不是被执行。

为什么不选 A？因为同一会话的历史是共享可变状态，并发写会导致消息顺序错乱和持久化冲突。

挑战观察这条链：_process_message 返回 OutboundMessage，但真正发送它的是 ChannelManager。为什么不让 AgentLoop 直接持有渠道对象、调用 channel.send()？列出至少三个理由。

这是"用队列而非直接调用"的经典权衡。理由至少有四条：

1. 依赖方向。 直接调用意味着 AgentLoop 必须 import 渠道类型， 核心层就被平台 SDK 污染了。而 SDK 的安装是可选的（见 scripts/install_channel_dependencies.py），核心层 import 它会让"不装 Telegram 依赖就跑不起来"。

2. 重试策略集中化。 BaseChannel.send() 的文档字符串明确写了 "Implementations should raise on delivery failure so the channel manager can apply any retry policy in one place"。重试逻辑统一在 ChannelManager._send_with_retry() （manager.py:905），而不是散落在 agent 里。

3. 多生产者。 除了回合的最终回复，还有很多地方要往外发消息： 进度提示（bus/progress.py）、内置命令的直接回复（command/builtin.py:440）、 cron 通知（cli/gateway_runtime.py:484）、message 工具的主动推送 （tools/message.py:79）、WebUI 的回合事件（session/webui_turns.py）。 它们共用同一个出口，就只需要一套路由与重试。

4. 背压与合并。 _dispatch_outbound() 有一个 pending 列表用于流式增量的合并（delta coalescing）——因为 asyncio.Queue 不支持 push_front。 这种跨消息的优化只有在集中的分发器里才做得到。

代价是：调用栈变得不连续，调试时要靠 session_key 串联日志。这也是为什么 TurnContext 里有一个 turn_id 字段。
