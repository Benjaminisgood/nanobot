Gateway 启动与定时任务

敲下 nanobot gateway 之后，谁创建了 MessageBus？谁启动了 AgentLoop 和 18 个渠道？Dream 又是在哪被定时叫醒的？ 答案几乎都在 cli/gateway_runtime.py 的 _run_gateway()。

一、装配：先接线，再跑循环

_run_gateway 前半段是同步装配（gateway_runtime.py:286 起）： 检查端口占用、准备 WebUI 静态包、把工作区模板同步到 disk，然后：

load_config() → MessageBus() → SessionManager / CronService / ChannelManager → make_provider() → AgentLoop.from_config(bus, …) → 把 cron 回调、WebUI coordinator 挂到 loop 上 → asyncio.run(run()) 进入常驻任务组

关键对象共享同一个 bus。渠道往 inbound 丢消息， loop 消费；loop / cron / 进度回调往 outbound 丢消息， ChannelManager.start_all() 里的 dispatcher 消费。 这和第 02、08 章画的图是同一条线， 只是现在能看见谁 new 了这些对象。

◆ 核心要点

Gateway 不是 第三种 agent 实现。它是「把已有零件拧在一起的进程主函数」。 Python SDK（nanobot/nanobot.py）可以只拧 AgentLoop，不拧渠道； Gateway 则把渠道、cron、健康检查、配置热更新全部拧上。

二、run()：一个事件循环里的任务组

默认常驻任务：

任务名职责
nanobot-config-watcher配置文件变更 → invalidate_runtime_config()，下一轮用新模型/工具开关
nanobot-agent-loop第 03 章的 AgentLoop.run()
nanobot-channels启动所有渠道 + outbound dispatcher
nanobot-local-triggers本地 trigger 队列（/trigger 创建的那种）
nanobot-health-server可选 HTTP 健康检查（默认开）

关闭策略：asyncio.wait(..., FIRST_COMPLETED) 等「运行时任务组」或「shutdown 事件」先完成。 任一常驻任务异常退出，整个 Gateway 进入 finally：停 cron、停 agent、 关 MCP/exec，然后 sessions.flush_all() 强制 fsync——呼应第 07 章 的耐久写入。

▲ 易错点：热更新不是热替换进程

配置 watcher 只调用 invalidate_runtime_config()。 已经在跑的 LLM 请求、已经 start() 的渠道不会被杀掉重来。 渠道 token 这类「启动期」配置通常仍需要重启 Gateway。 模型 preset、工具开关这类 loop 每轮会重新解析的项，改完就能在下一回合生效。

三、Cron：Dream 不走普通回合

CronService 到期后回调 on_cron_job。 大多数 job 会变成一条 inbound 消息交给 AgentLoop； 名为 dream 的内部 job 例外： 

        # Dream is an internal job — run directly, not through the agent loop.
        if job.name == "dream":
            from nanobot.agent.memory import DreamRunProgress, MemoryStore

            dream_session_key = MemoryStore.dream_session_key
            prune_dream_sessions = MemoryStore.prune_dream_sessions

            store = agent.context.memory
            progress = DreamRunProgress()
            resp = None
            diff_body = ""
            try:
                result = store.build_dream_prompt()
                if result is None:
                    logger.info("Dream: nothing to process")
                    return None
                prompt, last_cursor = result
                key = dream_session_key()
                dream_runtime = agent.dream_runtime()
                resp = await agent.process_direct(
                    prompt,
                    session_key=key,
                    ephemeral=True,
                    tools=store.build_dream_tools(),
                    on_progress=progress,
                    runtime=dream_runtime,
                )

对照第 07 章 的两阶段图：

  • Consolidator 在用户回合的 build / save 里跑
  • Dream 由 Gateway cron 叫醒，走 process_direct + 受限工具集，ephemeral=True
  • 只有 dream_run_completed 为真才推进 .dream_cursor，然后 Git commit + 裁剪 history
? 为什么 Dream 不 publish_inbound

若走普通 inbound，它会和用户抢同一把会话锁、污染用户 transcript、 还可能被 /stop 误杀。内部 job 用独立 dream:时间戳 session key， TTL 扫描也会跳过这个前缀（autocompact.py）。

同函数稍后处理 heartbeat：读工作区 HEARTBEAT.md， 有活跃任务才向某个会话提交系统回合。这是「周期自检待办」而不是又一个聊天渠道。

四、练习

基础nanobot gateway 最少会启动哪三个名为 nanobot-* 的 asyncio 任务？（不含可选健康检查）

配置热更新 nanobot-config-watcher、 核心循环 nanobot-agent-loop、 渠道 nanobot-channels。 另外还有 nanobot-local-triggers。Cron 是 await cron.start() 先启动，不一定叫这个名字的 task，但服务已在跑。

进阶改 config.json 里的 Telegram bot token 后，热更新会让渠道立刻换 token 吗？

不会。 watcher 只 invalidate_runtime_config()。 渠道在 start() 时用当时的 config 连上 SDK，token 属于启动期状态。 要换 token 需要重启 Gateway（或走渠道自己的 reload 路径，如果实现了）。 改默认模型 preset 则通常下一回合就会用新值。

挑战Dream cron 失败（工具报错或模型 error）时 cursor 会不会前进？history.jsonl 会不会被裁剪？

cursor 不前进：set_last_dream_cursor 包在 if completed: 里。 同一批 history 下次还会再喂给 Dream。

finally 里仍会 _commit_dream_changes、compact_history()、 prune_dream_sessions。也就是说：文件若已被工具改过，仍可能被 Git 记一笔； 但「这批 history 已处理完」这个进度不会谎报。这是「耐久副作用」和「消费游标」分开提交。

Gateway = 共享 bus 上的任务组 + 关机时 fsync。Dream/heartbeat 是这条进程里的内部 job， 刻意绕开用户会话锁。下一章看用户对话里的「再开一个 agent」——subagent。
