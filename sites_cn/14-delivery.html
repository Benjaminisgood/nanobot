第 14 章 · 运行时

流式投递与回合生命周期

Runner 通过回调吐出 token；用户看见的是 Telegram 气泡原地变长、WebUI 光标往前走。 中间这一层是 TurnDelivery：它不执行模型，只决定 「这条更新发到哪个 chat、算不算生命周期、stream_id 是什么」。

一、执行输入 vs 投递路由

TurnRoute 把「回复发到哪」从 InboundMessage 里拆出来。 系统消息尤其需要这个：subagent 的 inbound 是 channel="system"， 但用户应该在原来的 Telegram 群里看到结果。 

@dataclass(frozen=True)
class TurnRoute:
    """Turn delivery destination and lifecycle policy, separate from execution input."""

    channel: str
    chat_id: str
    metadata: dict[str, Any] = field(default_factory=dict)
    publish_lifecycle: bool = False

默认路由：普通用户消息 publish_lifecycle=True（进度、running、idle 都发）； channel == "system" 时把 chat_id 按 channel:id 拆开， 默认不发生命周期——避免 cron / subagent 把 WebUI 刷成「又开始了一轮」。 

    @staticmethod
    def _default_route(msg: InboundMessage, session_key: str) -> TurnRoute:
        if msg.channel != "system":
            return TurnRoute(
                channel=msg.channel,
                chat_id=msg.chat_id,
                metadata=dict(msg.metadata or {}),
                publish_lifecycle=True,
            )

Gateway 还可以注入 route_policy（WebUI 用来改标题、绑 websocket 会话）。 这正是 .agent/design.md 说的：wire 细节不属于 loop.py。

二、流式：两段开关 + stream_id

真正打开流式要同时满足：

  1. 工厂 create(..., enable_stream=True)（_dispatch 里是这样调的）
  2. 消息 metadata 带 _wants_stream（渠道 supports_streaming 时由基类写入，见第 08 章）
    def __post_init__(self) -> None:
        self.delivery_message = dataclasses.replace(
            self.input_message,
            channel=self.route.channel,
            chat_id=self.route.chat_id,
            metadata=dict(self.route.metadata),
        )
        self.lifecycle_message = (
            self.delivery_message if self.route.publish_lifecycle else self.input_message
        )
        if self.enable_stream and self.delivery_message.metadata.get("_wants_stream"):
            self._stream_base_id = f"{self.session_key}:{time.time_ns()}"

on_stream 在没有 base id 时返回 None——Runner 就走非流式路径。 有 id 时，每个 delta 变成 StreamDeltaEvent 丢进 outbound： 

    async def _publish_stream(self, delta: str) -> None:
        await self.bus.publish_outbound(
            outbound_message_for_event(
                channel=self.delivery_message.channel,
                chat_id=self.delivery_message.chat_id,
                event=StreamDeltaEvent(content=delta, stream_id=self._stream_id()),
                metadata=self.delivery_message.metadata,
            )
        )
        self._stream_open = True
◆ 核心要点：用 stream_id 而不是只靠 chat_id

同一聊天里可能交错：工具提示、思考块、正文、恢复后的第二段。 _stream_segment 在 stream_end(merge_next=False) 时加一。 渠道的 send_delta 文档要求按 stream_id 建缓冲区， 否则两段文字会糊进同一条消息。

/stop 取消时 abort_stream()：若流还开着，补发一次 end， 让飞书卡片 / Telegram 编辑态能收口，而不是永远转圈。

三、另一份拷贝：ContextGovernor

用户看见的流式文本，和送给下一轮 LLM 的 messages 不是同一份。 Runner 每次迭代先 context_governor.prepare_for_model： 

class ContextGovernor:
    """Prepare model-copy messages while preserving persisted history."""

    def prepare_for_model(
        self,
        config: ContextGovernanceConfig,
        messages: list[dict[str, Any]],
        compacted_tool_call_ids: set[str],
    ) -> list[dict[str, Any]]:
        updated = self.strip_placeholder_assistant_messages(messages)
        updated = self.strip_malformed_tool_calls(updated)
        updated = self.drop_orphan_tool_results(updated)
        updated = self.backfill_missing_tool_results(updated)
        updated = self.apply_tool_result_budget(config, updated)
        updated = self.compact_inflight_overflow(config, updated, compacted_tool_call_ids)
        updated = self.snip_history(config, updated)
        updated = self.drop_orphan_tool_results(updated)
        return self.backfill_missing_tool_results(updated)
▲ 易错点：治理结果不得写回 JSONL

第 04 章 Runner 注释写过：治理只修「模型那份拷贝」。 超长 exec 输出可能被截断或 offload 成文件路径再喂给模型， 但磁盘上的会话仍保留完整 tool 结果（受 max_tool_result_chars 等另一套限制）。 调试「模型怎么没看见那 200 行日志」时，先看 Governor，再怪渠道。

四、练习

基础渠道配置了 streaming: true，但子类没有 override send_delta。用户能看到逐 token 更新吗？

不能。 supports_streaming 要求配置为真 并且 type(self).send_delta is not BaseChannel.send_delta。 基类 no-op 时不会写 _wants_stream，TurnDelivery 也就不会分配 _stream_base_id。最终仍走完整 OutboundMessage.content。

进阶为什么 system 回合默认 publish_lifecycle=False？如果改成 True 会出现什么体验问题？

system inbound（subagent 完成、部分 cron）不是用户点的「新一轮对话」。 生命周期事件会让 WebUI 显示 running、刷新标题、推 turn 卡片。 全部打开等于后台任务每次完成都像用户又发了一句——状态栏闪烁、会话列表抖动。

投递路由仍然把 channel/chat_id 指回原聊天，所以可见回复可以有， 只是不广播「回合状态机」。

挑战流式已经输出半段，接着模型开始跑工具。TurnDelivery 如何避免工具结束后的新正文拼进同一条「正在编辑」的消息？指出相关字段。

Runner 在执行工具前会 on_stream_end(..., resuming=True)（第 04 章）。 _publish_stream_end 里若 merge_next=False， _stream_segment += 1，下一个 delta 的 stream_id 变成 base:1 而不是 base:0。

若 merge_next=True（length recovery 那种「同一答案接着写」）， _stream_open 保持 True、segment 不加，渠道应继续编辑同一缓冲区。 渠道必须按 stream_id 分桶，这是协议而不是建议。
