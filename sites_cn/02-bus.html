第 02 章 · 核心链路

消息总线与事件模型

整个项目最短的一个模块，也是形态影响最大的一个。bus/queue.py 只有 44 行—— 我们把它一行不漏地读完，然后讨论为什么这 44 行能撑起 18 个聊天平台。

一、完整源码：44 行的总线

"""Async message queue for decoupled channel-agent communication."""

import asyncio

from nanobot.bus.events import InboundMessage, OutboundMessage


class MessageBus:
    """
    Async message bus that decouples chat channels from the agent core.

    Channels push messages to the inbound queue, and the agent processes
    them and pushes responses to the outbound queue.
    """

    def __init__(self):
        self.inbound: asyncio.Queue[InboundMessage] = asyncio.Queue()
        self.outbound: asyncio.Queue[OutboundMessage] = asyncio.Queue()

    async def publish_inbound(self, msg: InboundMessage) -> None:
        """Publish a message from a channel to the agent."""
        await self.inbound.put(msg)

    async def consume_inbound(self) -> InboundMessage:
        """Consume the next inbound message (blocks until available)."""
        return await self.inbound.get()

    async def publish_outbound(self, msg: OutboundMessage) -> None:
        """Publish a response from the agent to channels."""
        await self.outbound.put(msg)

    async def consume_outbound(self) -> OutboundMessage:
        """Consume the next outbound message (blocks until available)."""
        return await self.outbound.get()

    @property
    def inbound_size(self) -> int:
        """Number of pending inbound messages."""
        return self.inbound.qsize()

    @property
    def outbound_size(self) -> int:
        """Number of pending outbound messages."""
        return self.outbound.qsize()

就这些。没有主题订阅、没有中间件、没有优先级、没有持久化、没有 ack 确认。

◆ 核心要点

两个无界 asyncio.Queue，四个方法，两个只读属性。 inbound 是"渠道 → agent"，outbound 是"agent → 渠道"。 方向是单向的，队列是分开的，所以永远不会出现"回复被当成新消息重新处理"这种环路。

逐点注意的三个细节

1. 泛型标注 asyncio.Queue[InboundMessage]。 这不是装饰，而是让 basedpyright 能在编译期发现"把 OutboundMessage 放进 inbound 队列"这类错误。 asyncio.Queue 在运行时不做类型检查，类型参数是唯一的防线。

2. 队列无界（没传 maxsize）。 这意味着 publish_inbound 实际上永远不会 await 挂起。 代价是没有天然背压：如果 agent 处理速度跟不上消息涌入，队列会无限增长。 项目把背压推到了别处——你会在第 03 章看到，真正限流的是会话锁和 _concurrency_gate，而不是队列长度。

3. inbound_size / outbound_size 只用于观测。 它们是 qsize() 的只读包装，供状态查询（如 /status 命令）使用。

? 为什么不用成熟的消息队列库

因为需求边界非常清楚：单进程内、同一事件循环、无需持久化、无需扇出。 Redis/RabbitMQ 会引入运维依赖；一个 pub-sub 框架会引入订阅注册表和主题命名规范。 而 .agent/design.md 的第二条约束就是"Less structure, more intelligence"—— 只有当结构消除了真实的复杂度时才引入它。

这里 44 行就够了，那就 44 行。需要多进程时，替换点也很清晰：只要保持这四个方法的签名， 内部换成任何实现都不影响上下游。

二、InboundMessage：渠道的统一出口

总线之所以能解耦，功劳其实在事件类型上。InboundMessage 定义了 "一条聊天消息在这个系统里长什么样"，18 个渠道都必须把自己的平台数据翻译成它： 

@dataclass
class InboundMessage:
    """Message received from a chat channel."""

    channel: str  # telegram, discord, slack, whatsapp
    sender_id: str  # User identifier
    chat_id: str  # Chat/channel identifier
    content: str  # Message text
    timestamp: datetime = field(default_factory=datetime.now)
    media: list[str] = field(default_factory=list)  # Media URLs
    metadata: dict[str, Any] = field(default_factory=dict)  # Channel-specific data
    session_key_override: str | None = None  # Optional override for thread-scoped sessions
    require_existing_session: bool = False

    @property
    def session_key(self) -> str:
        """Unique key for session identification."""
        return self.session_key_override or f"{self.channel}:{self.chat_id}"

字段设计的取舍

字段为什么是这个类型
channel: str 不是枚举。渠道是运行时发现的（插件可以来自第三方包），编译期无法穷举，所以只能是字符串。
content: str 纯文本。图片、位置、语音等全部被渠道"文本化"后拼进来（如 [location: 31.2, 121.5]），媒体的本地路径另放 media。这让核心层不必理解任何平台的富媒体结构。
media: list[str] 渠道已经把附件下载到本地并给出路径。核心层不做网络 IO，这也是安全边界的一部分。
metadata: dict[str, Any] 唯一的"逃生舱"。平台专属信息（message_id、话题 id、是否想要流式）都塞这里。这是有意保留的动态边界。
session_key_override 让渠道能覆盖默认会话键。Telegram 的话题（Topic）功能就靠它把同一群里的不同话题分成不同会话。
require_existing_session "只在会话已存在时才处理"。用于 cron / 自动化触发——不要因为一个定时任务而给用户凭空建一个新会话。

session_key：整个系统的分区键

那个 4 行的 @property 是全项目最高频被引用的一段逻辑：

    @property
    def session_key(self) -> str:
        """Unique key for session identification."""
        return self.session_key_override or f"{self.channel}:{self.chat_id}"

它同时决定了四件事：

  1. 历史归属——会话文件名是 base64url(session_key) + ".jsonl"
  2. 并发粒度——每个 session_key 一把 asyncio.Lock
  3. 压缩单位——TTL 空闲压缩按 session 扫描
  4. 命令作用域——/new、/stop、/model 都作用于当前 session

实际运行中会看到这些形态：

形态场景
telegram:123456默认规则：channel:chat_id
telegram:123456:topic:7Telegram 话题，由渠道通过 session_key_override 注入
unified:default开启 unified_session 后，所有渠道共享一个会话
dream:20260403-000210Dream 记忆整合的内部运行，用前缀隔离，不参与 TTL 扫描
▲ 易错点

msg.session_key 不一定是最终使用的会话键。AgentLoop 还有一层 _effective_session_key(msg)（loop.py:821）， 它在开启统一会话模式时会把所有键映射到 unified:default。

所以你在 loop.py 里会看到大量 effective_key != msg.session_key 的判断和 dataclasses.replace(msg, session_key_override=effective_key)—— 这是在把"有效键"回写进消息，保证下游（比如注入队列里的消息）看到的是一致的键。

三、OutboundMessage：回复与富交互

@dataclass
class OutboundMessage:
    """Message to send to a chat channel.

    ``event`` carries internal runtime/UI semantics. ``metadata`` is reserved
    for channel routing context (``message_id``, thread ids, etc.) and optional
    ``OUTBOUND_META_AGENT_UI`` blobs for rich clients.
    """

    channel: str
    chat_id: str
    content: str
    reply_to: str | None = None
    media: list[str] = field(default_factory=list)
    metadata: dict[str, Any] = field(default_factory=dict)
    buttons: list[list[str]] = field(default_factory=list)
    event: "OutboundEvent | None" = None

注意最后两个字段，它们体现了"如何在统一抽象下支持能力不均等的平台"这个经典问题的解法：

buttons: list[list[str]] —— 二维数组表示按钮的行列布局。 Telegram / 飞书能渲染成内联键盘；邮件渠道直接忽略它。 能力探测由渠道自己做，核心层只负责表达意图。

event: OutboundEvent | None —— 内部运行时/UI 语义。 这是理解"进度提示"、"流式增量"、"回合结束"这些非用户文本消息的关键。

event 与 metadata 的分工

docstring 里那句话值得展开：

原文

"event carries internal runtime/UI semantics. metadata is reserved for channel routing context (message_id, thread ids, etc.) and optional OUTBOUND_META_AGENT_UI blobs for rich clients."

  • event = 这条消息是什么（进度？增量？终态？）——语义
  • metadata = 这条消息发到哪（回复哪条？哪个话题？）——路由

nanobot/bus/events.py 顶部定义了几个约定键，都是内部用的： 

# Optional ``OutboundMessage.metadata`` key for structured, channel-agnostic UI
# payloads. Value is JSON-serializable with at least ``kind``; rich clients may
# render it and other channels may ignore unknown keys.
OUTBOUND_META_AGENT_UI = "_agent_ui"

# Internal-only inbound metadata used by in-process channels to ask the agent
# loop to update runtime state without going through a user session.
INBOUND_META_RUNTIME_CONTROL = "_runtime_control"
RUNTIME_CONTROL_ACK = "_ack"
RUNTIME_CONTROL_MCP_RELOAD = "mcp_reload"
RUNTIME_CONTROL_IMAGE_GENERATION_RELOAD = "image_generation_reload"
RUNTIME_CONTROL_SESSION_DISCARD = "session_discard"

INBOUND_META_RUNTIME_CONTROL 特别有意思：它让 WebUI 能通过同一条消息总线要求 agent 重载 MCP 服务器或丢弃会话，而不需要伪造一个用户回合。 处理入口在 AgentLoop.run() 的第一个判断：

✓ 实用提示

这也是"运行时改配置立刻生效"的实现路线。想加一种新的运行时控制指令， 在 bus/events.py 加一个常量、在 agent_context.handle_runtime_control 加一个分支即可，完全不用碰七阶段流水线。

四、进度回调：把回调转成总线事件

agent 内部产生的"进度"（正在调用什么工具、思考过程、流式文本）不是通过返回值传出来的， 而是通过回调函数。bus/progress.py 负责把回调翻译成总线消息： 

def build_bus_progress_callback(
    bus: MessageBus,
    msg: InboundMessage,
) -> Callable[..., Awaitable[None]]:
    """Return a callback that publishes progress as outbound messages."""

    async def _publish_progress(
        content: str,
        *,
        tool_hint: bool = False,
        tool_events: list[dict[str, Any]] | None = None,
        file_edit_events: list[dict[str, Any]] | None = None,
        reasoning: bool = False,
        reasoning_end: bool = False,
    ) -> None:
        await bus.publish_outbound(
            outbound_message_for_event(
                channel=msg.channel,
                chat_id=msg.chat_id,
                event=ProgressEvent(
                    content=content,
                    tool_hint=tool_hint,
                    reasoning_delta=reasoning,
                    reasoning_end=reasoning_end,
                    tool_events=tool_events,
                    file_edit_events=file_edit_events,
                ),
                metadata=msg.metadata,
            )
        )

这是一个闭包工厂：它捕获 bus 和原始 msg， 返回一个只接受内容的回调。这样 AgentRunner 里就不需要知道 bus 的存在—— 它只调用 spec.progress_callback(...)。

文件头的 docstring 还划清了一条边界： "Runtime state notifications such as turn lifecycle and model changes live in nanobot.bus.runtime_events." ——用户可见的进度输出和内部运行时状态通知是两个不同的模块， 这正是 .agent/design.md 里"运行时状态扇出遵循同一边界"那条约束的落地。

五、练习

基础MessageBus 的两个队列都没有设置 maxsize。这带来什么后果？项目在哪里补上了限流？

后果：没有背压。

asyncio.Queue() 默认 maxsize=0 表示无界， 所以 await queue.put(msg) 永远不会真正挂起等待。 理论上如果消息涌入速度持续超过处理速度，内存会一直涨。

限流补在三个地方：

  • 会话锁（loop.py:2338 的 _get_session_lock）—— 同一会话严格串行，天然限制了单会话的并发。
  • 全局并发闸门 self._concurrency_gate（_dispatch 里 async with lock, gate）——限制同时进行的回合总数。
  • 注入队列有界——_dispatch 里创建的是 asyncio.Queue(maxsize=20)，并且 put_nowait 遇到 QueueFull 时会降级为"回退到排队任务"，而不是阻塞。

设计上的取舍很清楚：让入口尽量不阻塞（避免拖慢平台 SDK 的回调）， 把限流放在真正消耗资源的地方（LLM 调用）。

进阶为什么 InboundMessage.media 是"本地文件路径"而不是"URL"？字段注释里明明写的是 # Media URLs。

这是一个注释与实现已经漂移的地方——很好的源码阅读训练：注释会过期，调用点不会。

看 Telegram 渠道的实际填充逻辑（channels/telegram/runtime.py:1546 附近）：

        # Download current message media
        current_media_paths, current_media_parts = await self._download_message_media(
            message, add_failure_content=True
        )
        media_paths.extend(current_media_paths)
        content_parts.extend(current_media_parts)
        if current_media_paths:
            self.logger.debug("Downloaded message media to {}", current_media_paths[0])

变量名就是 media_paths，来自 _download_message_media—— 渠道在发布消息前就已经把附件下载到本地了。

为什么必须这样设计？三个理由：

  • 凭证隔离。 Telegram 的文件 URL 需要 bot token 才能下载。 如果传 URL，核心层和所有工具都得知道渠道的凭证——这会彻底破坏解耦。
  • 安全边界。 核心层不做出网 IO，是第 10 章 SSRF 防护的前提。让 agent 去 fetch 一个来自外部消息的 URL 是典型的 SSRF 面。
  • 时效性。 平台的媒体 URL 通常几分钟就过期，而消息可能在队列里等待、 或在压缩后被回放。本地路径才是稳定引用。

阅读方法论：判断一个字段的真实语义，要看写入方（渠道）而不是注释。 在 Cursor 里对 media= 全局搜索，几秒钟就能确认。

挑战假设你要给系统加一个"消息已读回执"能力：agent 收到消息后先给平台发一个"已读"标记，再开始处理。请判断这该放在哪一层，并说明如果放错层会有什么后果。

结论：放在渠道层，而且不应该经过总线。

判断依据——问三个问题：

  1. 这个能力所有平台都有吗？ 没有。Telegram 有 sendChatAction， 邮件没有已读回执的对等概念。→ 说明它不是统一抽象的一部分。
  2. agent 的决策会影响它吗？ 不会。"已读"是收到消息就该发的， 与 LLM 说什么无关。→ 说明它不需要穿过核心层。
  3. 它需要平台凭证/SDK 吗？ 需要。→ 只有渠道持有这些。

三个答案都指向渠道层。具体位置：在渠道自己的消息处理函数里， 调用 self._handle_message(...) 之前 直接调平台 API。 比如 Telegram 就是在 _process_message_update 里加一行。

如果放错层，会发生什么：

  • 放进 OutboundMessage 加一个 mark_read: bool 字段？ 这会污染统一抽象——18 个渠道里 17 个必须忽略这个字段，而且它和 content 的语义完全不同（一个是"发文本"，一个是"改状态"）。 更糟的是时序：outbound 要等回合结束才发，"已读"就变成"回复完了才已读"，失去意义。
  • 放进 AgentLoop.run()？ 核心层就得判断 if msg.channel == "telegram"——这正是 .agent/design.md 明令禁止的：能放在渠道适配器里的特性，不应内联进 agent 循环。
  • 用 OutboundEvent 新增一种事件类型？ 这是三个错误方案里最接近合理的，但仍然多绕了一圈（agent → bus → manager → channel）， 换来的只是延迟增加和一个只有一个渠道用得上的事件类型。

通用判据：如果一个能力的"输入"和"输出"都在同一层内部， 就不要让它穿过总线。总线只承载跨越所有权边界的数据。

本章小结

44 行的总线 + 两个 dataclass = 18 个平台的解耦。关键在于 InboundMessage 把"富媒体的平台消息"降维成"文本 + 本地路径 + metadata 逃生舱"。 下一章进入核心层的上半场：AgentLoop 如何调度这些消息。
