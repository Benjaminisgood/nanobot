第 13 章 · 运行时

子 Agent

主 agent 用 spawn 工具把长任务交给另一个 AgentRunner 实例。 子 agent 不复用主会话 JSONL，工具集更窄，完成后把结果当成 channel="system" 的 inbound 塞回主会话——常常走进第 03 章讲过的注入队列。

参数行为
wait=false（默认）SubagentManager.spawn：立刻返回「已启动」，后台跑
wait=truerun_inline：当前工具调用阻塞到子任务结束，结果当 tool result 返回

起点渠道 / chat / session 全部来自 RequestContext（第 06 章的 ContextVar）， 所以子 agent 知道「结果该通知谁」，而不需要 LLM 把 chat_id 当参数传来传去。

二、隔离：自己的工具注册表

◆ 核心要点：scope="subagent" 切断递归

Tool._scopes 默认只有 {"core"}。 文件系统、shell、web、search、apply_patch 显式加入了 "subagent"； spawn / message / cron / long_task 没有。 因此子 agent 不能再 spawn，也不能给用户发消息或改持续目标。 这是用发现范围做的权限模型，不必在 Runner 里写特殊 if。

提示词也更瘦：_build_subagent_prompt 渲染 agent/subagent_system.md，只附 skills 摘要， 不走主 agent 那套完整 identity + bootstrap + MEMORY 栈。

注释写尽了第 03 章的不变量：必须用有效 session key 覆盖， 否则统一会话模式下结果会变成另一个 _dispatch，和主回合并发写同一份历史。

主 loop 的 _build_turn 看到 TurnKind.SYSTEM 且 sender_id == "subagent" 时，会把结果早持久化，但喂给模型时当成新输入 （loop.py:1763 那段注释）——因为很多 provider 会丢掉末尾 assistant 消息。

▲ 易错点：wait=true 不走这条 inbound

run_inline(..., announce=False)。结果只作为 spawn 工具的返回值出现在 当前 ReAct 循环的 tool 消息里。不会再触发一轮「系统消息回合」。 适合「我必须先知道子任务结论才能继续」的咨询场景。

五、取消与会话绑定

_session_tasks 记录「这个主会话养了哪些 task_id」。 /stop 或丢弃会话时 cancel_by_session 会 task.cancel() 并关掉该会话名下的 exec 会话。 子 agent 不是孤儿进程——生命周期挂在主会话上。

六、练习

基础子 agent 能不能再调用 spawn？依据是哪条机制？

不能。 ToolLoader().load(..., scope="subagent") 会跳过 _scopes 不含 subagent 的类。 SpawnTool 使用基类默认 {"core"}，因此不会被注册。 这比在 execute 里写 if is_subagent: return error 更干净——未注册的工具模型根本看不到。

进阶主 agent 正在跑（持有会话锁），后台 subagent 完成并 publish_inbound。这条系统消息会新建 _dispatch 吗？

通常不会。有效 key 已在 _pending_queues 里， 调度循环第 5 道分流会 put_nowait 进注入队列 （03 章）。 主 Runner 在工具批次结束后的 _try_drain_injections 把它拼进 messages，再进行下一轮 LLM。

若主回合已经结束、队列已拆除，这条消息会走正常 _dispatch，成为新的 SYSTEM 回合—— 这也是 _build_turn 里 subagent 分支必须能独立处理的原因。

挑战对比 wait=true 与默认后台 spawn：在「主模型上下文窗口」和「用户可见延迟」上各有什么代价？什么时候不该用 wait？

wait=true：子任务的全部中间 tool 结果不进入主会话 JSONL； 只有最终字符串作为一条 tool result。主上下文更干净，但用户会感觉当前回合卡住 （要等子 Runner 的 max_iterations）。 主会话锁一直被占着，/stop 可以取消主任务从而取消这次 inline（同一条 cancel 链）。

后台 spawn：主模型立刻继续想下一件事；用户能先看到「已启动」。 代价是稍后多一轮 system 注入，主上下文会再吃一段 announce 文本。 多个后台任务还受全局并发上限约束。

不该用 wait 的典型情况：任务可能超过主回合墙钟超时、或需要用户同时看到主 agent 的流式输出。 该用 wait 的情况：下一步的工具参数严格依赖子任务结论（否则主模型会靠猜继续跑）。

本章小结

子 agent = 缩小的 Tool 范围 + 独立 Runner + 用总线把结果送回有效 session key。 它没有新的循环算法，只是把第 04 章的 Runner 嵌套调用了一次。 下一章看 token 如何变成用户看见的流式更新：TurnDelivery。
