第 03 章 · 核心链路

AgentLoop：七阶段流水线

2344 行，全项目最大的单文件，也是.agent/design.md 里明确标记为"受保护关键路径"的一半。 但它的结构其实非常清晰：一个调度器 + 一个七阶段流水线。 这一章我们把这两件事拆开读透。

一、先划清职责：AgentLoop 做什么、不做什么

类的 docstring 已经把职责写得很直白：

class AgentLoop:
    """
    The agent loop is the core processing engine.

    It:
    1. Receives messages from the bus
    2. Builds context with history, memory, skills
    3. Calls the LLM
    4. Executes tool calls
    5. Sends responses back
    """

但真正关键的是它不做什么。这条边界写在架构约束里：

◆ 核心要点：状态扇出的所有权边界

AgentLoop 可以从 nanobot.bus.runtime_events 发布通用运行时事件（回合/运行/模型/目标状态变化）， 但 WebUI/WebSocket 的协议细节——比如 _turn_end、 _goal_status、标题刷新、目标状态同步——属于 nanobot.session.webui_turns.WebuiTurnCoordinator 或相应的渠道适配器。

判据：如果一段代码里出现了某个客户端专属的字段名，它就不该在 loop.py 里。

二、run()：调度循环的六道分流

run() 是常驻任务。它的核心是一个 while self._running 循环， 每次取一条消息，然后做六次分流判断——只有全部不命中，才真正创建处理任务。

2.1 取消息：1 秒超时的心跳设计

            while self._running:
                try:
                    msg = await asyncio.wait_for(self.bus.consume_inbound(), timeout=1.0)
                except asyncio.TimeoutError:
                    self._check_expired_sessions_if_due()
                    continue
                except asyncio.CancelledError:
                    # Preserve real task cancellation so shutdown can complete cleanly.
                    # Only ignore non-task CancelledError signals that may leak from integrations.
                    if not self._running or task_is_cancelling():
                        raise
                    logger.warning(
                        "Ignoring leaked CancelledError while consuming inbound messages"
                    )
                    continue
                except Exception as e:
                    logger.warning("Error consuming inbound message: {}, continuing...", e)
                    continue

三个异常分支，每一个都对应一个真实教训：

TimeoutError → 心跳。 timeout=1.0 不是为了避免死等（consume_inbound 本来就是可取消的协程）， 而是为了获得一个周期性的执行时机。这一秒的空闲被用来跑 _check_expired_sessions_if_due()——扫描空闲超时的会话并触发压缩。 这样就不需要额外起一个定时任务。

CancelledError → 区分"真取消"与"泄漏取消"。 这是异步编程里非常隐蔽的坑。第三方集成（比如某些 SDK 内部用 anyio cancel scope） 可能让 CancelledError 冒泡到这里，但进程并没有要退出。 如果无脑 raise，整个 agent 就被一个第三方 bug 干掉了； 如果无脑忽略，进程又永远关不掉。所以这里用 not self._running or task_is_cancelling() 做判别： 只有"我们自己要停"或"当前任务确实处于取消中"，才尊重这个取消信号。

其他 Exception → 记日志继续。 调度循环是最高优先级的常驻任务，绝不能因为单条消息的问题而退出。

✓ 实用提示

_check_expired_sessions_if_due()（loop.py:1142）内部自己做节流： "Scan idle sessions no more often than the configured interval"。 也就是说虽然每秒都会调它，但真正扫描的频率由配置决定（默认 60 秒）。 把"调用时机"和"执行频率"解耦，是这类心跳设计的常用手法。

2.2 六道分流：顺序即优先级

取到消息后的判断顺序不能调换，每一层都假定前面的层已经过滤掉了某类消息：

1
运行时控制指令 agent_context.handle_runtime_control(...)。WebUI 要求重载 MCP、丢弃会话等。 这类消息根本不是"对话"，必须最先拦掉。
↓ 不是
2
要求已存在会话但会话不存在 msg.require_existing_session and self.sessions.get_cached(...) is None → continue。 静默丢弃。cron/自动化触发不该凭空创建会话。
↓ 通过
3
优先命令 self.commands.is_priority(raw) → _dispatch_command_inline(..., dispatch_priority)。 典型是 /stop、/restart。它们必须在会话锁之外执行—— 否则 /stop 会排在它要取消的那个任务后面，永远等不到。
↓ 不是
4
自动化回合延后 遍历 self._automation_turn_coordinators，若 defer_if_active(...) 返回真则跳过。会话正忙时，cron 触发的回合延后而不是插队。
↓ 不需延后
5
会话正忙 → 回合中注入 effective_key in self._pending_queues。这是本章第四节的重点。 注意内部还有一层：普通斜杠命令要 inline 分发，不能进注入队列。
↓ 空闲
6
创建处理任务 asyncio.create_task(self._dispatch(msg))，并登记到 self._active_tasks[effective_key]，用 add_done_callback 自动摘除。

最后这一步值得看原文，因为它解释了 /stop 为什么能找到要取消的任务：

                # Compute the effective session key before dispatching
                # This ensures /stop command can find tasks correctly when unified session is enabled
                task = asyncio.create_task(self._dispatch(msg))
                active_tasks = self._active_tasks.setdefault(effective_key, set())
                active_tasks.add(task)
                task.add_done_callback(active_tasks.discard)
▲ 易错点：为什么是 effective_key 而不是 msg.session_key

开启统一会话（unified_session）后，所有渠道的消息都映射到 unified:default。 如果任务登记用 msg.session_key（比如 telegram:123）， 而 /stop 查找时用有效键 unified:default，就找不到任务—— 表现为"/stop 没反应"。这条注释就是为了防止后人改回去。

三、_dispatch()：会话锁与善后

_dispatch 的 docstring 一句话说清了并发模型： "Process a message: per-session serial, cross-session concurrent." 

    async def _dispatch(self, msg: InboundMessage) -> None:
        """Process a message: per-session serial, cross-session concurrent."""
        session_key = self._effective_session_key(msg)
        if session_key != msg.session_key:
            msg = dataclasses.replace(msg, session_key_override=session_key)
        lock = self._get_session_lock(session_key)
        gate = self._concurrency_gate or nullcontext()

注意第 4-5 行：如果有效键和消息自带的键不同，就用 dataclasses.replace 造一个新消息把有效键写回去。 InboundMessage 虽然是普通 dataclass（可变），但代码风格上把它当不可变对象处理—— 这样后续任何持有这条消息引用的地方（注入队列、自动化协调器）看到的键都是一致的。

然后是双重上下文管理：

            async with lock, gate:
                # Only the task that owns the session lock may publish the
                # active mid-turn injection queue for this session.
                pending = asyncio.Queue(maxsize=20)
                self._pending_queues[session_key] = pending
◆ 核心要点：锁的所有权即队列的所有权

_pending_queues[session_key] 的存在，就是"这个会话正忙"的标志。 而只有拿到会话锁的任务才有权注册它。这个不变量让第 5 道分流（回合中注入） 可以用一次字典查找代替复杂的状态机——非常漂亮的简化。

3.1 finally 块：三件必须做的善后

_dispatch 的 finally 块（loop.py:1335 起）是全文最容易被忽略但最重要的部分。它做三件事： 

                finally:
                    # Drain any messages still in the pending queue and re-publish
                    # them to the bus so they are processed as fresh inbound messages
                    # rather than silently lost.  Only remove our own queue; a
                    # later task waiting on the lock must not be able to steal
                    # cleanup ownership.
                    queue = None
                    if self._pending_queues.get(session_key) is pending:
                        queue = self._pending_queues.pop(session_key, None)
                    else:
                        queue = pending
                    if queue is not None:
                        leftover = 0
                        while True:
                            try:
                                item = queue.get_nowait()
                            except asyncio.QueueEmpty:
                                break
                            await self.bus.publish_inbound(item)
                            leftover += 1
                        if leftover:
                            logger.info(
                                "Re-published {} leftover message(s) to bus for session {}",
                                leftover, session_key,
                            )

第一件：只清理自己的队列。

if self._pending_queues.get(session_key) is pending 用的是 is 身份比较，不是 in。为什么？ 设想会话 A 的任务 1 正在收尾，任务 2 已经拿到锁并注册了自己的队列。 如果任务 1 无脑 pop(session_key)，就会把任务 2 的队列删掉—— 于是任务 2 变成"看起来空闲"，第 5 道分流失效，同一会话出现并发。 注释里那句 "a later task waiting on the lock must not be able to steal cleanup ownership" 说的就是这个竞态。

第二件：残留消息重新入队，不静默丢弃。

队列里可能还有没被注入的消息（比如 LLM 提前收尾了）。它们被 publish_inbound 送回 inbound 总线，下一轮当作新消息处理。 这保证了用户发的每条消息最终都会被响应。

第三件：释放流式与状态。

delivery.idle() 通知前端"回合结束"， _publish_next_deferred_automation_turn() 把之前延后的 cron 回合放出来。

3.2 取消路径：保住已经做完的工作

用户按 /stop 时会抛 CancelledError。这里的处理很有讲究： 

                    # Preserve partial context from the interrupted turn so
                    # the user does not lose tool results and assistant
                    # messages accumulated before /stop.  The checkpoint was
                    # already persisted to session metadata by
                    # _emit_checkpoint during tool execution; materializing
                    # it into session history now makes it visible in the
                    # next conversation turn.
                    if session_key in self._discarding_sessions:
                        raise
                    try:
                        key = self._effective_session_key(msg)
                        session = self.sessions.get_or_create(key)
                        if self._restore_runtime_checkpoint(session):
                            self._clear_pending_user_turn(session)
                            self.sessions.save(session)
? 为什么要"检查点"这套机制

想象 agent 已经跑了 5 分钟、执行了 12 个工具调用，用户此刻按下 /stop。 如果什么都不保存，那 12 个工具的结果（可能包括昂贵的 web 搜索、已经写好的文件分析）全部消失， 用户下一句话得从零开始。

所以 AgentRunner 在工具执行的两个时点（awaiting_tools 和 tools_completed）会调用 _emit_checkpoint， 把当前的 assistant 消息和已完成的工具结果写进 session metadata。 取消时 _restore_runtime_checkpoint 再把它"物化"成正式的会话历史。

注意那个前置判断 if session_key in self._discarding_sessions: raise—— 如果这次取消的原因本身就是用户要丢弃会话（/new），那就别恢复了， 直接把取消传播出去。

四、TurnContext：阶段之间的唯一载体

七阶段流水线的每个阶段签名都是 async def stage(ctx: TurnContext) -> ...。 所有中间状态都挂在这个 dataclass 上： 

@dataclass
class TurnContext:
    msg: InboundMessage
    session_key: str
    turn_id: str
    runtime: LLMRuntime | None
    kind: TurnKind
    delivery: TurnDelivery
    original_user_text: str | None = None
    session: Session | None = None

    history: list[dict[str, Any]] = field(default_factory=list)
    initial_messages: list[dict[str, Any]] = field(default_factory=list)
    provider_state: ProviderConversationState | None = field(default=None, repr=False)
    request_context: RequestContext | None = None
    runtime_context_blocks: list[RuntimeContextBlock] = field(default_factory=list)

字段是按生命周期分组的：第一组在构造时就有；第二组由 build 阶段填充；第三组由 run 阶段填充。

用 require_* 把"阶段顺序"变成类型安全

runtime 和 session 声明成 | None， 因为在早期阶段它们确实还不存在。但后续阶段每次都写 if ctx.runtime is None 会很啰嗦。作者的解法是两个访问器： 

    def require_runtime(self) -> LLMRuntime:
        """Return the runtime established by the BUILD stage."""
        if self.runtime is None:
            raise RuntimeError("turn runtime is not initialized; BUILD must run before this stage")
        return self.runtime

    def require_session(self) -> Session:
        """Return the session established by the RESTORE stage."""
        if self.session is None:
            raise RuntimeError("turn session is not initialized; RESTORE must run before this stage")
        return self.session
◆ 核心要点：这是一种"文档即代码"的技巧

返回类型是 LLMRuntime（不带 None），所以调用方拿到的是确定类型， basedpyright 不会报错，也不需要 cast—— 符合"每个 cast 必须有运行时检查支撑"那条约束，因为这里就是那个运行时检查。

更妙的是异常消息本身就是文档："BUILD must run before this stage"。 新人如果在错误的阶段访问，报错信息直接告诉他阶段依赖关系。

五、七阶段流水线

整个 _process_message 的最后 9 行，就是全部编排：

        await self._run_turn_stage(ctx, "restore", self._restore_turn)
        await self._run_turn_stage(ctx, "compact", self._compact_session)
        if await self._run_turn_stage(ctx, "command", self._dispatch_command):
            return ctx.outbound
        await self._run_turn_stage(ctx, "build", self._build_turn)
        await self._run_turn_stage(ctx, "run", self._run_turn)
        await self._run_turn_stage(ctx, "save", self._persist_turn)
        await self._run_turn_stage(ctx, "respond", self._prepare_outbound)
        return ctx.outbound

command 阶段是唯一有返回值的——如果它返回 True （消息是一条被成功处理的斜杠命令），流水线直接短路返回， 不进入 LLM。这就是"/status 不消耗 token"的实现。

_run_turn_stage：统一的可观测性包装

    async def _run_turn_stage(
        self,
        ctx: TurnContext,
        name: str,
        handler: Callable[[TurnContext], Awaitable[_T]],
    ) -> _T:
        started_at = time.perf_counter()
        try:
            result = await handler(ctx)
        except Exception:
            duration_ms = (time.perf_counter() - started_at) * 1000
            logger.debug(
                "[turn {}] Stage {} failed after {:.1f}ms",
                ctx.turn_id,
                name,
                duration_ms,
            )
            raise

一个 5 行的装饰器式包装，换来每个阶段的耗时日志， 用 ctx.turn_id 串联。注意它用 _T 泛型保留了 handler 的返回类型， 所以 command 阶段的 bool 能正确传出来。

✓ 实用提示：这是调试 nanobot 最快的入口

把日志级别设为 DEBUG，发一条消息，你会看到七行 Stage X completed in Y ms。 哪个阶段慢一目了然：build 慢通常是压缩或技能加载， run 慢是 LLM/工具，save 慢是磁盘 fsync。

build 阶段的一个精妙细节：早持久化

_build_turn 里有一步叫 _persist_user_message_early。 为什么要在调 LLM 之前就把用户消息写盘？

? 为什么这样设计

因为 LLM 调用可能持续几分钟，期间进程可能崩溃、被 kill、或用户 /stop。 如果等回合结束才一起写盘，用户那句话就丢了——下次对话时 agent 完全不知道用户问过什么。

代价是引入了"半个回合"的持久化状态，所以需要配套的 _mark_pending_user_turn / _restore_pending_user_turn （loop.py:2132、2252）来标记和恢复。 这是"崩溃安全"和"状态简洁"之间的一次明确取舍。

还有一处同类的取舍，在 subagent 结果的处理上——注释写得非常清楚：

        if is_subagent:
            # Keep the durable internal delivery as an assistant record, but
            # present this completion to the model as fresh follow-up input.
            # Providers without assistant-prefill support drop trailing
            # assistant messages, so using the persisted record as the current
            # prompt would hide an independently dispatched subagent result.
            subagent_followup_persisted = self._persist_subagent_followup(
                session,
                ctx.msg,
            )

翻译一下：subagent 的结果持久化时是 assistant 消息（这才符合它的真实语义）， 但喂给模型时当作新的用户输入。因为很多 provider 会丢弃末尾的 assistant 消息 （不支持 assistant prefill），如果直接用持久化的形态当 prompt，模型根本看不到 subagent 干了什么。

六、回合中注入：让 agent"边干边听"

这是 nanobot 最有体感的功能之一：agent 在跑长任务时，你追加一句话，它能立刻纳入考虑。 实现分布在三处，串起来看：

① 调度侧（loop.py:1214 起） 会话正忙 → msg 塞进 self._pending_queues[key]（maxsize=20） 队列满 → 降级为普通排队任务（不阻塞、不丢弃） ② 注入队列的桥接（loop.py:1094 的 _drain_pending） 作为 AgentRunSpec.injection_callback 传给 runner ③ 消费侧（runner.py 的 _try_drain_injections） 在两个安全点被调用： · 工具执行完成后、下一次 LLM 调用前 · 工具出错后 取出消息 → _append_injected_messages() 追加为 user 消息 → continue 下一轮迭代
▲ 易错点：为什么只在这两个点注入

因为 OpenAI/Anthropic 的消息序列有合法性约束： 每个 assistant 消息带的 tool_calls，必须紧跟着对应数量的 role="tool" 结果消息。如果在"已发出 tool_calls、还没回填结果"时插入一条 user 消息，请求会直接被 API 拒绝。

所以注入点只能选在工具序列已经闭合的时刻。这也解释了 _append_injected_messages（runner.py:163）为什么要做角色交替检查—— 连续两条 user 消息在某些 provider 上同样非法，得先合并。

七、练习

基础run() 的调度循环里，为什么 /stop 这类"优先命令"必须在会话锁之外处理？

因为它要取消的正是持有那把锁的任务。

_dispatch() 的结构是 async with lock, gate:， 锁在整个回合期间被持有。如果 /stop 也走 _dispatch()， 它会在 async with lock 处挂起，等待前一个任务释放锁—— 而前一个任务正等着 /stop 来取消它。典型的死等 （不是死锁，因为 LLM 最终会返回，但用户体验上等于 /stop 失效）。

所以 run() 在第 3 道分流用 _dispatch_command_inline(...) 直接在调度循环里执行，不碰锁。对应的取消实现是 _cancel_active_tasks(key)（loop.py:798）， 它遍历 self._active_tasks[key] 逐个 task.cancel()。

这也是为什么第 6 道分流那两行注释强调必须用 effective_key 登记任务—— 登记的键和查找的键必须一致。

进阶_dispatch() 的 finally 块用 is 而不是 in 来判断该不该清理队列。构造一个具体的时序，说明如果写成 if session_key in self._pending_queues: self._pending_queues.pop(...) 会出什么 bug。

会导致同一会话出现并发处理。时序如下：

t0 任务A 拿到会话锁，注册 _pending_queues["tg:1"] = QueueA t1 任务A 的 _process_message 返回，进入 finally 前的收尾逻辑 （delivery.complete、automation coordinator 等，都是 await 点） t2 ← 事件循环切换 → 任务A 让出控制权 t3 任务B 拿到会话锁（A 已退出 async with 的锁作用域） 覆盖 _pending_queues["tg:1"] = QueueB t4 → 切回任务A 的 finally 错误写法：`in` 判断为真 → pop 掉了 QueueB！ t5 任务C 的消息到达调度循环 第 5 道分流检查 "tg:1" in self._pending_queues → False → 误判为空闲 → asyncio.create_task(_dispatch(msgC)) t6 任务C 与任务B 同时处理 "tg:1"

后果是两个任务同时读写同一份会话历史：消息顺序错乱、 _persist_turn 互相覆盖（后写的把先写的新消息抹掉）、 并且 /stop 只能取消其中一个。

is 比较的正确性来自一个不变量： 每个 _dispatch 调用创建的 pending 队列对象都是独一无二的。 所以 self._pending_queues.get(key) is pending 成立， 就精确表示"字典里现在放的还是我注册的那个"。

顺带看 else 分支：queue = pending。 即使字典里的已经不是自己的，也仍然要把自己队列里的残留消息排空重发—— 否则那些消息就真的丢了。

挑战_build_turn 里在调用 LLM 之前就把用户消息写盘（_persist_user_message_early）。这引入了一个"半个回合已持久化"的中间状态。请说明：(1) 这个状态如何被标记；(2) 如果进程在此刻崩溃，下次启动时如何恢复；(3) 为什么不用"写盘但打删除标记"这种更简单的方案。

(1) 如何标记

靠 session metadata 里的一个标志位，由这三个方法维护 （loop.py:2132–2141）： _mark_pending_user_turn(session) 打标记、 _clear_pending_user_turn(session) 清标记、 _clear_runtime_checkpoint(session) 清检查点。 正常回合走完 save 阶段后标记会被清掉。

(2) 如何恢复

在 restore 阶段的末尾，两个恢复动作依次执行： 

        if self._restore_runtime_checkpoint(session):
            self.sessions.save(session)
        if self._restore_pending_user_turn(session):
            self.sessions.save(session)

注意顺序：先恢复检查点，再恢复待处理的用户回合。 因为检查点里可能已经包含了部分 assistant/tool 消息， 它们在时间上早于"这个用户回合还没答完"这个结论。 两次恢复各自独立 save，保证任一步失败都不会留下半写状态。

(3) 为什么不用"软删除标记"

三个理由：

  • 存储格式不支持原地改。 会话是 JSONL， 写入方式是"全量重写 tmp 文件 + os.replace"（见第 07 章）。要给某条消息打删除标记，就得重写整个文件—— 和现在的成本完全一样，没有省任何东西。
  • 回放路径会被污染。 会话历史的读取者不止一个： get_history() 喂给 LLM、Consolidator 做摘要、 read_session 工具给 agent 自己查、WebUI 渲染 transcript。 引入"软删除"意味着每个读取者都得记得过滤， 漏一个就是一个 bug。而现在的方案把复杂度收敛在 restore 阶段一处。
  • 语义不同。 "这条消息该删掉"和"这条消息已收到但还没回答" 是两件事。后者是有用信息——恢复时 agent 应该回答它， 而不是忘掉它。软删除表达不了"待处理"这个含义。

这题的通用启示：选择状态表示时，先问"有几个读取者"。 读取者越多，越应该让不变量在写入侧成立，而不是要求每个读取侧都做过滤。

本章小结

AgentLoop = 六道分流的调度器 + 七阶段的回合流水线 + TurnContext 这个状态载体。 它负责"什么时候、以什么上下文"调用 LLM，但真正的 ReAct 循环在下一章的 AgentRunner 里。
