第 06 章 · 能力层

工具系统

LLM 决定"要做什么"，工具系统负责"真的去做"。 nanobot/agent/tools/ 共 26 个文件——从读写到 shell、MCP 桥接、子 agent 派发。 这一章读透 Tool 抽象、自动发现、三层校验 和 错误契约，理解 AgentRunner 如何把 model 的 function call 变成可观测的副作用。

一、Tool 抽象基类：execute 是唯一入口

每个工具继承 Tool（base.py:156）。四个抽象成员： name、description、parameters（三个 @property） 和 async def execute(self, **kwargs) -> Any。 注意统一入口是 execute，不是 run。

◆ 核心要点

read_only / concurrency_safe / exclusive 控制并行执行策略——AgentRunner 可以把多个只读工具（glob、grep）并发跑， 但 exclusive 工具（如 shell）必须独占。

_scopes / enabled(ctx) / create(ctx) 是插件元数据：ToolLoader 按 scope 过滤、按配置决定是否注册、 用工厂方法注入 ToolContext（workspace、bus、cron 等）。

二、错误契约：ToolResult 而非异常

class ToolResult(str):
    """String-compatible tool output with structured status."""

    is_error: bool

    def __new__(cls, content: str, *, is_error: bool = False) -> ToolResult:
        obj = str.__new__(cls, content)
        obj.is_error = is_error
        return obj

    @classmethod
    def error(cls, content: str) -> ToolResult:
        return cls(content, is_error=True)

工具失败返回 ToolResult.error(...)，不抛异常。 ToolRegistry.execute 只在真正意外（代码 bug）时 catch Exception。 这样 LLM 总能收到结构化的错误文本，进入"分析错误、换策略"的 ReAct 循环。

? 为什么不抛异常

对 LLM 来说，"文件不存在"和"权限拒绝"是可恢复的业务错误， 应该变成 tool result 消息喂回模型。抛异常会让 runner 走通用 Error executing {name}: ... 路径，丢失工具自己的上下文； 更糟的是 uncaught exception 可能中断整个回合。

ToolResult 继承 str 是为了向后兼容——旧工具返回 plain string 仍然有效。

三、pkgutil 自动发现与 entry-point 插件

内置工具不走手动注册表。ToolLoader.discover() 扫描 nanobot/agent/tools/ 下所有模块： 

    def discover(self) -> list[type[Tool]]:
        if self._test_classes is not None:
            return list(self._test_classes)
        if self._discovered is not None:
            return self._discovered
        seen: set[int] = set()
        results: list[type[Tool]] = []
        for _importer, module_name, _ispkg in pkgutil.iter_modules(self._package.__path__):
            if module_name.startswith("_") or module_name in _SKIP_MODULES:
                continue
            try:
                module = importlib.import_module(f".{module_name}", self._package.__name__)
            except Exception:
                logger.exception("Failed to import tool module: %s", module_name)
                continue
            for attr_name in dir(module):
                attr = getattr(module, attr_name)
                if (
                    isinstance(attr, type)
                    and issubclass(attr, Tool)
                    and attr is not Tool
                    and not attr_name.startswith("_")
                    and not getattr(attr, "__abstractmethods__", None)
                    and getattr(attr, "_plugin_discoverable", True)
                    and id(attr) not in seen
                ):
                    seen.add(id(attr))
                    results.append(attr)
        results.sort(key=lambda cls: cls.__name__)
        self._discovered = results
        return results

_SKIP_MODULES（loader.py:20）跳过基础设施模块 （base、registry、mcp 等）。 MCP 工具由 connect_mcp_servers 动态注册，设了 _plugin_discoverable = False。

load() 检查 _scopes 与 enabled(ctx)， 调 tool_cls.create(ctx) 再 registry.register(tool)： 

    def load(self, ctx: ToolContext, registry: ToolRegistry, *, scope: str = "core") -> list[str]:
        registered: list[str] = []
        builtin_names: set[str] = set()
        sources = [(self.discover(), False), (self._discover_plugins().values(), True)]
        for source, is_plugin_source in sources:
            for tool_cls in source:
                cls_label = tool_cls.__name__
                try:
                    if scope not in getattr(tool_cls, "_scopes", {"core"}):
                        continue
                    if not tool_cls.enabled(ctx):
                        continue
                    tool = tool_cls.create(ctx)
                    if is_plugin_source:
                        tool = _LegacyErrorPrefixTool(tool)
                    if registry.has(tool.name):
                        if is_plugin_source and tool.name in builtin_names:
                            logger.warning(
                                "Plugin %s skipped: conflicts with built-in tool %s",
                                cls_label, tool.name,
                            )
                            continue
                        logger.warning(
                            "Tool name collision: %s from %s overwrites existing",
                            tool.name, cls_label,
                        )
                    registry.register(tool)
                    registered.append(tool.name)
                    if not is_plugin_source:
                        builtin_names.add(tool.name)
                except Exception:
                    logger.exception("Failed to register tool: %s", cls_label)
        return registered

ToolRegistry.get_definitions() 批量导出，内置工具排前、 mcp_ 前缀排后，结果缓存到 _cached_definitions： 

    def get_definitions(self) -> list[dict[str, Any]]:
        """Get tool definitions with stable ordering for cache-friendly prompts.

        Built-in tools are sorted first as a stable prefix, then MCP tools are
        sorted and appended. The result is cached until the next
        register/unregister call.
        """
        if self._cached_definitions is None:
            definitions = [tool.to_schema() for tool in self._tools.values()]
            builtins: list[dict[str, Any]] = []
            mcp_tools: list[dict[str, Any]] = []
            for schema in definitions:
                name = self._schema_name(schema)
                if name.startswith("mcp_"):
                    mcp_tools.append(schema)
                else:
                    builtins.append(schema)

            builtins.sort(key=self._schema_name)
            mcp_tools.sort(key=self._schema_name)
            self._cached_definitions = builtins + mcp_tools

        return self._cached_definitions

最终在 AgentRunner._call_provider 里传给 LLM：

✓ 实用提示

稳定排序（builtins 前缀 + MCP 后缀）让 prompt cache 命中率更高—— 同一套内置工具定义在多次请求间字节级一致，只有 MCP 工具增减时才 invalidate。

五、三层校验管线：prepare_call

这是本章最有价值的片段之一。模型返回的 tool call 在执行前经过 ToolRegistry.prepare_call()： 

    def prepare_call(
        self,
        name: str,
        params: Any,
    ) -> tuple[Tool | None, Any, str | None]:
        """Resolve, cast, and validate one tool call."""
        tool = self._tools.get(name)
        if not tool:
            suggestion = self._suggest_name(str(name))
            hint = f" Did you mean '{suggestion}'? Tool names must match exactly." if suggestion else ""
            return None, params, (
                ToolResult.error(
                    f"Error: Tool '{name}' not found.{hint} Available: {', '.join(self.tool_names)}"
                )
            )
        # Compatibility for external tools that still implement the legacy
        # setter protocol. Built-ins read the authoritative ContextVar
        # directly and never copy routing state.
        if isinstance(tool, ContextAware) and (ctx := current_request_context()) is not None:
            tool.set_context(ctx)

        params = self._coerce_params(tool, params)
        if not isinstance(params, dict):
            return tool, params, (
                ToolResult.error(
                    f"Error: Tool '{name}' parameters must be a JSON object, got "
                    f"{type(params).__name__}. Use named parameters like "
                    'tool_name(param1="value1", param2="value2") matching the tool schema.'
                )
            )

        cast_params = tool.cast_params(cast(dict[str, Any], params))
        errors = tool.validate_params(cast_params)
        if errors:
            return tool, cast_params, (
                ToolResult.error(f"Error: Invalid parameters for tool '{name}': " + "; ".join(errors))
            )
        return tool, cast_params, None
prepare_call 三层管线 ① 工具名解析 — _tools.get(name) + _suggest_name 拼写建议 ② 参数 JSON coercion — _coerce_params（字符串 → dict、unwrap {"arguments": ...}） ③ 类型转换 + schema 校验 — cast_params + validate_params

execute() 在 prepare 之后捕获意外异常： 

    async def execute(self, name: str, params: Any) -> Any:
        """Execute a tool by name with given parameters."""
        hint = "\n\n[Analyze the error above and try a different approach.]"
        tool, params, error = self.prepare_call(name, params)
        if error:
            return ToolResult.error(str(error) + hint)

        try:
            assert tool is not None  # guarded by prepare_call()
            result = await tool.execute(**params)
            if is_tool_error_result(result):
                return ToolResult.error(str(result) + hint)
            return result
        except Exception as e:
            return ToolResult.error(f"Error executing {name}: {str(e)}" + hint)
▲ 易错点

模型经常把参数包成 {"arguments": "{\"path\": \"...\"}"} 双层嵌套。 _unwrap_arguments_payload（registry.py:176）专门处理这个—— 但如果 schema 里真的有一个叫 arguments 的参数，就不会 unwrap。

超时解析在 _resolve_timeout：默认 60s、LLM 传入上限 600s、 配置 timeout=0 表示不限： 

    def _resolve_timeout(self, timeout: int | None) -> int | None:
        """Resolve the effective hard timeout in seconds (None = no limit).

        A per-call timeout supplied by the model stays capped at _MAX_TIMEOUT so
        the LLM cannot request unbounded execution. The config-level default
        (self.timeout) may exceed that cap, and 0 disables the limit entirely
        for trusted long-running tasks (#3595).
        """
        if timeout:
            return min(timeout, self._MAX_TIMEOUT)
        if self.timeout and self.timeout > 0:
            return self.timeout
        return None

MCP 工具同样用 asyncio.wait_for(session.call_tool(...))： 

                result = await asyncio.wait_for(

? 为什么 LLM 传入 timeout 有 600s 上限

模型可能幻觉出 timeout=999999。min(timeout, _MAX_TIMEOUT) （shell.py:417，_MAX_TIMEOUT = 600）防止 agent 被单次工具调用无限挂起。 信任的长任务走配置级 timeout=0，不经过 LLM 参数。

九、练习

基础为什么工具统一用 execute 而不是 run？失败时应该抛异常还是返回 ToolResult.error？

execute 是 Tool 抽象基类定义的唯一定义入口（base.py:223）， ToolRegistry.execute 也只调这个方法——命名一致避免"到底调 run 还是 execute"的分叉。

失败应返回 ToolResult.error(...)（base.py:228）。 docstring 写得很清楚："return content, or ``ToolResult.error(...)`` for failures"。 这样错误文本作为 role="tool" 消息喂回 LLM，进入正常的 ReAct 纠错循环； 抛异常只留给真正的代码 bug，由 registry.execute 的 except Exception（registry.py:200）兜底。

进阶模型调用 exec 工具时传入 {"arguments": "{\"command\": \"ls\"}"}（双层嵌套）。 prepare_call 如何处理？如果工具的 schema 里真的有一个叫 arguments 的参数呢？

正常情况：unwrap 一层。

_coerce_params → _unwrap_arguments_payload（registry.py:176）： 当 params 只有唯一 key "arguments"，且 schema 的 properties 里 没有 名为 arguments 的字段时，把值当作 JSON 字符串再 parse 一次， 得到 {"command": "ls"}。

例外：schema 真有 arguments 参数。

此时 "arguments" in properties 为真，不会 unwrap—— 双层嵌套会被当作合法的单参数对象传给 cast_params。 这是有意设计：不能误伤那些参数名就叫 arguments 的工具。

如果 unwrap 后仍不是 dict，prepare_call 第 132 行返回 "parameters must be a JSON object" 错误，不会执行工具。

挑战MCP server 注册了一个名叫 my.tool@v2 的工具。 说明从 MCP 连接到 LLM 可见 schema 的完整命名/transform 链路，以及为什么要 _sanitize_mcp_tool_name + SHA1 截断。

链路：

  1. connect_mcp_servers（mcp.py:983）连接 server → list_tools() 拿到 MCPToolDefinition。
  2. MCPToolWrapper.__init__（mcp.py:592）构造本地名： f"mcp_{server_name}_{tool_def.name}" → 如 mcp_myserver_my.tool@v2。
  3. _sanitize_mcp_tool_name（mcp.py:178）： @ 和 . 替换成 _ → mcp_myserver_my_tool_v2。
  4. 若超过 64 字符（_MAX_TOOL_NAME_LENGTH，mcp.py:164）， 截断前缀 + _ + SHA1 前 8 位后缀，保证 OpenAI function name 合法且唯一。
  5. registry.register(wrapper) → get_definitions() 排到 MCP 后缀 → 传给 provider（runner.py:919）。
  6. LLM 返回 tool call 时用 sanitized 名 → prepare_call 解析 → MCPToolWrapper.execute 调 session.call_tool(self._original_name, ...) 用原始 MCP 名 my.tool@v2 调远端。

为什么必须 sanitize： OpenAI function calling 只允许 [a-zA-Z0-9_-]；MCP 工具名来自第三方，可能含空格、Unicode、特殊符号。 不消毒会导致 schema 被 provider 拒收，或不同 MCP 工具映射到同名冲突。

本章小结

工具系统 = Tool.execute 统一入口 + ToolResult 错误契约 + pkgutil/entry-point 发现 + prepare_call 三层校验 + MCP 桥接。Provider 决定"调什么"，Registry 决定"怎么调、调哪个"—— 两者在第 04 章 的 ReAct 循环里汇合。
