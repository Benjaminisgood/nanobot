第 17 章 · 总结

综合练习与实战

前 16 章按链路拆开读了 nanobot 的骨架。这一章不分模块—— 用自测题检验你是否能在脑子里串起数据流，用三个动手任务验证「扩展点」是否真的理解， 最后用一条调试路线应对「agent 没回复」这类真实故障。 建议顺序：先闭卷做自测 → 再挑一个动手任务 → 最后扫一遍调试清单。

一、跨章节自测

难度分布：3 基础 / 4 进阶 / 3 挑战。答案含源码位置，可点击跳回对应章节。

基础把下面函数按「一条用户消息从渠道到回复」的执行顺序排列：

  • A AgentRunner.run()
  • B Channel._handle_message() → bus.publish_inbound()
  • C AgentLoop.run() → _dispatch()
  • D ChannelManager 消费 outbound 队列
  • E AgentLoop._process_message() 七阶段流水线

正确顺序：B → C → E → A → D

  1. 渠道收消息，封装 InboundMessage，publish_inbound（02 章）
  2. AgentLoop.run() 消费 inbound，分流后 create_task(_dispatch)（03 章）
  3. _process_message：restore → compact → command → build → run → save → respond（loop.py:1541-1548）
  4. run 阶段调用 AgentRunner.run() 做 ReAct 循环（04 章）
  5. respond 后 outbound 入队，渠道 manager 发送（02 章 / 08 章）

基础下面三处改动，分别该落在哪一层？

  • 1 Telegram 群聊按 topic 拆分 session
  • 2 新增 /export slash 命令
  • 3 工具调用失败后自动换 fallback model

1 → 渠道层：设置 InboundMessage.session_key_override（08 章，参考 Telegram 的 topic session key）。不要改 loop.py。

2 → 命令层：在 builtin.py 加 handler + register_builtin_commands（09 章）。

3 → Provider 层：FallbackProvider 包装主 provider（05 章）——主模型返回 error 时切到 fallback 链。工具失败本身通常是「喂回模型」而非换模型（04 章）。

基础restrict_to_workspace 配置项在旧版 JSON 里写在 tools.exec.restrictToWorkspace。新版应该写在哪？加载时谁负责迁移？

新版写在顶层 tools.restrictToWorkspace（Python: config.tools.restrict_to_workspace）。 _migrate_config()（loader.py:347-358，09 章） 在 validate 前把旧键提升到顶层。

进阶同一会话连发两条用户消息 M1、M2，M1 的 _dispatch 还在跑。 M2 到达时会发生什么？M2 是 slash 命令 /help 呢？

普通消息 M2：命中 effective_key in self._pending_queues（loop.py:1214）， 放入 pending queue 等待注入——不会创建第二个 dispatch 任务（03 章）。

/help：is_dispatchable_command 为真 → inline dispatch（loop.py:1217-1221），不排队——命令响应不应被长回合阻塞。

进阶为什么不能在对 tool 结果的处理中，随意插入一条新的 role: user 消息到会话历史？

LLM API 要求消息序列合法：assistant 带 tool_calls 后必须跟 tool 结果； 不能在没有 assistant 的前提下插入 user。 AgentRunner 维护严格的 message list（04 章）； 违规会导致 provider 400 或模型行为异常。

工具错误应通过 role: tool 消息返回（或 ToolResult.error 字符串作为 tool content）， 而不是伪造 user 消息。

进阶会话有 200 条消息，last_consolidated = 150。 get_history() 回放时从哪开始？Dream 归档时处理哪一段？

last_consolidated 是归档进度指针，不是 replay 边界（session/manager.py:210-212，07 章）。

  • Replay（get_history）：从 last_consolidated 起取未归档后缀，但至少保留尾部 8 条（MIN_COMPACTED_REPLAY_MESSAGES），并回溯到合法的 user turn 边界
  • Consolidator（阶段一）：对 messages[last_consolidated:boundary] 做 LLM 摘要，写入 history.jsonl，再推进指针（边界选择见 pick_consolidation_boundary，memory.py:844 起）
  • Dream（阶段二）：读 history.jsonl 里 cursor > .dream_cursor 的条目，编辑 SOUL.md / USER.md / MEMORY.md——它不直接扫 session.messages

索引 0–149 已摘要进 history（或 raw dump），默认不再整段送进 LLM 上下文。

进阶Provider 流式输出已推送 500 token 文本后连接断开。 should_retry_guard 此时返回什么？为什么？

返回 False——禁止盲目重试（05 章， base.py:912：should_retry_guard=lambda: not has_streamed_content）。

已有 partial content 时重试会导致用户看到重复片段或消息序列不一致。 首次失败后 should_retry_guard 会被置 None 允许后续重试路径调整（base.py:1096）。

挑战工具执行时磁盘满导致 OSError，与参数校验失败，应分别返回什么？ 为什么 SSRF 拦截也不抛异常？

契约（06 章）：

  • 可恢复的业务/环境错误 → return ToolResult.error("…")，runner 把文本作为 tool 结果喂回模型
  • 参数不合法 → 多数工具在 execute 入口返回 ToolResult.error；Schema 校验失败同理
  • 不应让整回合崩溃的错误 → 绝不裸抛到 runner 外（除非真正的 invariant 破坏）

SSRF / 工作区边界返回 error 字符串 + runner _classify_violation（runner.py:1568，10 章）—— 抛异常会中断 ReAct 循环；软失败让模型换策略，反复违规才升级硬失败。

挑战对比两种攻击：(1) 允许列表里的 symlink 读 /etc/passwd； (2) DNS 重绑定访问 169.254.169.254。各自由哪层防御？

(1) Symlink：_is_path_exactly_allowed() 比较 logical vs resolved 路径键 （workspace_policy.py:60-68，10 章）。 仅 resolve() 检查不够。

(2) DNS rebinding：resolve_url_target 校验 IP + PinnedDNSAsyncTransport 钉扎 DNS（network.py:264-285）+ 重定向二次校验 validate_resolved_url。 仅校验 URL 字符串不够——必须钉死连接时的 IP。

挑战启用 tools.exec.sandbox: "bwrap" 但在 Windows 上运行。 命令实际如何执行？配置上的 restrictToWorkspace 还有效吗？

shell.py:467-472：打 warning 后无沙箱运行原生 shell。 bwrap 是 Linux 容器场景的能力，代码诚实声明而非 silent fallback。

restrict_to_workspace 仍生效——它是应用层 _guard_command 路径检查（shell.py:808 起）， 与 bwrap 独立（10 章）。 生产环境 Windows 应靠受限用户账户 + allow/deny 正则，而非 bwrap。

二、动手任务

任务 A（入门）：实现 word_count 工具

目标：新建只读工具，统计给定文本或文件的词数。

涉及文件：nanobot/agent/tools/word_count.py（新建）

要求：

  • 继承 Tool，实现 4 个抽象成员：name、description、parameters、execute
  • read_only = True；按需设置 config_key
  • 文件名不以 _ 开头，且不在 _SKIP_MODULES 里（loader.py:20-23）

验收：启动 gateway 或跑测试，确认 ToolRegistry.tool_names 包含 word_count。

提示：参考 filesystem.py 的 Tool 子类结构；pkgutil 扫描自动发现，无需改 registry。

任务 B（中级）：渠道自定义 session_key

目标：为某渠道（如 Matrix 或自建 WebSocket 客户端）实现「每 thread/topic 独立会话」。

涉及文件：对应 nanobot/channels/<name>/runtime.py

要求：

  • 构造 InboundMessage 时设置 session_key_override（参考 Feishu feishu:oc:om 模式，08 章）
  • 不修改 loop.py——session 拆分是渠道职责

验收：同 chat 不同 thread 的消息写入不同 JSONL 文件；/history 互不干扰。

任务 C（进阶）：注册 OpenAI 兼容 Provider

目标：添加一个指向自建网关的 provider，factory 能路由到它。

涉及文件：

  • nanobot/providers/registry.py — PROVIDERS 加 ProviderSpec
  • nanobot/config/schema.py — ProvidersConfig 加对应字段

要求：若 endpoint 完全 OpenAI 兼容，可能只需 registry + schema，不必新写 provider 类（05 章）。

验收：nanobot provider list 可见新 provider；配置 API key 后能完成一次 chat。

三、调试路线：「agent 没回复」

从症状出发，按顺序收窄范围。每步给出建议日志关键字。

用户: "agent 没回复" │ ▼ [1] 日志级别 DEBUG，搜 "stage" │ loop.py _run_turn_stage 会记录七阶段耗时 │ 卡在哪一 stage？ restore / build / run / save？ ▼ [2] 搜 "_dispatch" / "create_task" │ run() 六道分流是否把消息 continue 掉了？ │ require_existing_session？ runtime_control？ ▼ [3] 搜 'finish_reason == "error"' / "LLM returned error" │ provider 是否返回 finish_reason="error"？ │ runner 会把错误内容当 final_content；loop 侧有 logger.error ▼ [4] 搜 "ToolResult" / "tool_call" / "blocked by" │ 工具是否返回 ToolResult.error？ │ SSRF / workspace / deny pattern？ ▼ [5] 搜 "publish_outbound" / "outbound" │ respond 阶段是否产出 OutboundMessage？ │ outbound 队列是否有消费者？ ▼ [6] 渠道层：搜 channel 名 + "send" / "Failed" │ Telegram/Discord API 是否拒发？ ▼ [7] 仍无头绪 → 检查 pairing / allowFrom 空 allowFrom 默认拒绝（SECURITY.md）
✓ 实用提示

同步发一条 /status（priority 命令，不经锁）确认 event loop 存活、 provider 连通、inbound/outbound queue 深度——再决定深入哪一层。

五、本章最后一题

挑战用一句话说明 nanobot 的「边缘层」（第 08–10 章）与「核心链路」（第 02–04 章）的职责边界。

核心链路回答「消息如何被调度、回合如何执行」——与具体平台、具体配置文件格式无关。 边缘层回答「外部世界如何被翻译成核心能理解的形状」——渠道协议、JSON 配置、camelCase、 slash 命令、安全策略——并且遵循核心的所有权边界（不把 WebUI 协议塞进 loop，不把已读回执塞进 bus）。

判据（01 章 / 02 章）： 如果一段代码需要某个平台的 token 或用户 JSON 的键名，它属于边缘层； 如果只处理 InboundMessage / TurnContext / ToolResult，它属于核心或能力层。

本章小结

读懂 nanobot 不是记住 18 个渠道的名字——而是能在故障时说出「问题在 bus / loop / runner / provider / 渠道 / 配置哪一层」。 回到 目录页 标记进度，或带着动手任务的 PR 去贡献代码。祝阅读愉快。
